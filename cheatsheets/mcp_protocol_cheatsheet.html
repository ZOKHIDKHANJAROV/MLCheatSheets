🔌 Model Context Protocol (MCP)

📅 Ноябрь 2026

🔷 1. Суть

Model Context Protocol (MCP) — открытый протокол, по которому ИИ-приложение подключается к внешним инструментам и источникам данных одним и тем же способом. Его представила компания Anthropic в конце 2024 года.

Идея похожа на единый разъём: приложение и сервер договариваются о формате сообщений один раз, и дальше любой совместимый клиент работает с любым совместимым сервером.

  • Сервер описывает свои инструменты, данные и шаблоны
  • Клиент узнаёт о них и даёт модели возможность их использовать
  • Обмен идёт сообщениями JSON-RPC

🔷 2. Проблема N×M

Без стандартаС MCP
N приложений, M системN × M своих коннекторовN клиентов + M серверов
Пример 4 × 520 интеграций9 реализаций
Новая системадописать под каждое приложениеодин сервер для всех

Каждый коннектор приходилось писать и поддерживать отдельно. Стандартный протокол превращает произведение в сумму.

🔷 3. Клиент и сервер

  • Host — приложение с моделью (чат, IDE, агент)
  • Client — компонент внутри host: держит одно соединение с одним сервером
  • Server — программа, которая открывает возможности: файлы, базы, API
  • Один host может держать несколько клиентов и подключаться ко многим серверам

Модель сама серверам не звонит: решения о вызовах принимает host, который общается с моделью.

🔷 4. Три типа возможностей

ТипЧто этоКто решает использовать
Toolsфункции, которые что-то делают (поиск, запись, запрос)модель
Resourcesданные для контекста: файлы, записи, документыприложение
Promptsготовые шаблоны запросов, часто с параметрамипользователь

Кроме них, клиент может предоставлять серверу собственные возможности, например запросить у модели продолжение (sampling).

🔷 5. Транспорты

ТранспортКак работает
stdiohost запускает сервер как подпроцесс; сообщения идут через stdin/stdout
HTTPсервер доступен по сети; запросы клиента идут по HTTP, ответы могут приходить потоком
  • stdio — просто и локально, без сети
  • HTTP — для удалённых серверов, нужна аутентификация
  • Формат сообщений одинаков для обоих транспортов

🔷 6. Обмен JSON-RPC

# запрос клиента: есть method и id
{"jsonrpc": "2.0", "id": 2, "method": "tools/list"}

# ответ сервера: тот же id, result
{"jsonrpc": "2.0", "id": 2, "result": {"tools": [
    {"name": "search", "description": "Поиск по базе",
     "inputSchema": {"type": "object"}}]}}

# вызов инструмента
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "search", "arguments": {"q": "agents"}}}

# уведомление: нет id, ответа не ждёт
{"jsonrpc": "2.0", "method": "notifications/initialized"}

# ошибка: error с code и message
{"jsonrpc": "2.0", "id": 3, "error": {"code": -32602, "message": "..."}}

Ответ связывается с запросом по id. Сообщение без id — уведомление.

🔷 7. Жизненный цикл

клиент                          сервер
  | -- initialize ------------>  |   версия протокола, возможности
  | <-- результат -------------   |   что умеет сервер
  | -- notifications/initialized  |   клиент готов
  | -- tools/list ------------>  |   каталог инструментов
  | -- tools/call ------------>  |   работа
  | <-- result / error --------   |
  | (закрытие соединения)         |

На этапе initialize стороны согласуют версию и то, какие возможности каждая поддерживает.

🔷 8. Сервер-заглушка на Python

import json

TOOLS = {"echo": lambda args: args.get("text", "")}

def handle(line):
    msg = json.loads(line)
    if "id" not in msg:                          # уведомление
        return None
    if msg["method"] == "tools/list":
        result = {"tools": [{"name": n} for n in TOOLS]}
    elif msg["method"] == "tools/call":
        p = msg["params"]
        result = {"content": [{"type": "text",
                               "text": TOOLS[p["name"]](p["arguments"])}]}
    else:
        return json.dumps({"jsonrpc": "2.0", "id": msg["id"],
                           "error": {"code": -32601, "message": "нет метода"}})
    return json.dumps({"jsonrpc": "2.0", "id": msg["id"], "result": result})

req = {"jsonrpc": "2.0", "id": 1, "method": "tools/call",
       "params": {"name": "echo", "arguments": {"text": "привет"}}}
print(handle(json.dumps(req)))

Это учебная схема: готовые SDK берут на себя разбор сообщений, версии и транспорт.

🔷 9. Права и безопасность

  • Относитесь к серверу как к стороннему коду: ставьте только доверенные
  • Минимальные права: доступ только к нужным папкам и данным
  • Опасные действия (запись, удаление, отправка) — с подтверждением пользователя
  • Результаты инструментов — данные, не команды: в них может быть prompt injection
  • Проверяйте аргументы вызова и ограничивайте объём ответа
  • Для HTTP нужна аутентификация; не храните секреты в описаниях инструментов
  • Ведите журнал вызовов

🔷 10. Плюсы и минусы

Плюсы

  • один сервер подходит многим приложениям
  • модель получает каталог возможностей автоматически
  • разделение: владелец системы пишет сервер, приложение — клиент

Минусы

  • у каждого подключённого сервера свои риски доверия
  • много инструментов раздувают контекст и путают модель
  • дополнительный слой: процесс, транспорт, отладка
  • протокол развивается — следите за версией

🔷 11. Когда использовать

  • нужны одни и те же интеграции в нескольких приложениях
  • хотите подключить готовые серверы вместо самописных коннекторов
  • агенту нужен единый каталог инструментов и данных
  • для одной функции в одном приложении проще обычный вызов функции

🔷 12. Частые ошибки

  • ❌ подключить слишком много инструментов сразу
  • ❌ слепо доверять стороннему серверу
  • ❌ ждать ответа на уведомление (нет id)
  • ❌ путать result и error
  • ❌ нет таймаута на вызов инструмента
  • ❌ писать в описание инструмента секреты
«MCP — это стандарт подключения, а не гарантия безопасности: права и доверие остаются на вас.»

📏 Оценка ИИ-агентов

📅 Ноябрь 2026

🔷 1. Суть

Агент — LLM в цикле «думать → вызвать инструмент → увидеть результат». Его ответ недетерминирован и зависит от длинной цепочки шагов, поэтому одного прогона на одной задаче мало.

Что оцениваем:

  • Результат: решена ли задача (task success)
  • Надёжность: решается ли она каждый раз (pass^k)
  • Траекторию: шаги, токены, стоимость, латентность
  • Безопасность и политику: не нарушил ли агент правила по пути
Оценка агента — это эксперимент: фиксированный набор задач, повторы, метрики и логи трасс.

🔷 2. Ключевые понятия

  • Задача (task): начальное состояние + цель + способ проверки
  • Попытка (trial): один независимый прогон агента на задаче
  • Трасса (trace): полный журнал шагов — сообщения, вызовы инструментов, ответы, время, токены
  • Оценщик (grader): код-проверка, сравнение с эталоном или LLM-судья
  • Среда (environment): песочница с состоянием, которое можно проверить после прогона (файлы, БД)
  • Регрессионный набор: задачи, которые раньше ломались и не должны сломаться снова

🔷 3. Успешность задачи

Лучше проверять конечное состояние среды (тесты прошли, запись в БД создана), а не красоту текста.

success = 1, если проверка пройдена
success_rate = (1/N) · Σ success_i

# доля частичного успеха
score = (выполненные подцели) / (все подцели)

Доверительный интервал важен: при N = 50 задачах разница в 3 п.п. между версиями агента легко оказывается шумом.

🔷 4. pass@k и pass^k

Пусть на задаче сделано n попыток, из них c успешных.

pass@k  = 1 − C(n−c, k) / C(n, k)
# вероятность, что среди k попыток
# есть хотя бы одна успешная

pass^k  = C(c, k) / C(n, k)
# вероятность, что все k попыток успешны

# при истинной доле успеха p:
pass@k → 1 − (1−p)^k   (растёт с k)
pass^k → p^k           (падает с k)

pass@k — «может ли агент решить вообще» (хорошо для генерации кода с проверкой). pass^k — «можно ли на него положиться» (клиентский сервис, где каждый сбой — проблема).

Пример: p = 0.8, k = 4 → pass@4 ≈ 0.998, но pass^4 = 0.8⁴ ≈ 0.41.

🔷 5. Код: оценщики pass@k и pass^k

from math import comb

def pass_at_k(n, c, k):
    """Несмещённая оценка pass@k."""
    if n - c < k:
        return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n, c, k):
    """Оценка pass^k: все k попыток успешны."""
    return comb(c, k) / comb(n, k)

rows = [(10, 8), (10, 3), (10, 10)]  # (n, c)
for k in (1, 4):
    a = sum(pass_at_k(n, c, k) for n, c in rows) / len(rows)
    b = sum(pass_hat_k(n, c, k) for n, c in rows) / len(rows)
    print(k, round(a, 3), round(b, 3))

Метрику считают по задачам, затем усредняют по набору. Нельзя считать «1 − (1 − p̂)^k» от общей доли — это смещённая оценка.

🔷 7. LLM-as-a-judge

Другая LLM оценивает ответ или трассу по рубрике. Нужен там, где нет точной проверки (качество текста, вежливость, обоснованность).

Типичные смещения:

  • Позиционное: предпочтение первого (или последнего) варианта
  • Многословность: длинные ответы кажутся лучше
  • Самопредпочтение: судья выше оценивает ответы своей же модели
  • Чувствительность к формулировке рубрики и шкалы

Что делать: менять порядок вариантов и усреднять, давать чёткую рубрику с примерами, брать судью другой модели, калибровать на размеченных людьми примерах (согласие судьи с человеком), где можно — заменять код-проверкой.

🔷 8. Код: судья с обменом позиций

def judge_stub(question, a, b):
    """Заглушка вместо вызова LLM: 'A' или 'B'."""
    return "A" if len(a) >= len(b) else "B"  # смещение!

def compare(question, ans1, ans2):
    first = judge_stub(question, ans1, ans2)
    second = judge_stub(question, ans2, ans1)
    # результат принимаем, только если он
    # не зависит от порядка
    if first == "A" and second == "B":
        return "ans1"
    if first == "B" and second == "A":
        return "ans2"
    return "tie"

print(compare("Q", "коротко", "очень длинный ответ"))

Если вердикт меняется при обмене мест — это сигнал позиционного смещения, а не различия в качестве.

🔷 9. Бенчмарки (общие принципы)

  • SWE-bench: исправление реальных issue из репозиториев GitHub; успех — прохождение тестов
  • GAIA: вопросы для универсального ассистента, требующие поиска, работы с файлами и рассуждений; ответ короткий и проверяемый
  • WebArena: задачи в самодостаточных веб-средах (магазин, форум и т. п.); проверка по итоговому состоянию
  • τ-bench: диалог агента с имитируемым пользователем по правилам домена; сравнивается состояние БД, вводится метрика pass^k

Принципы: проверяемость результата, воспроизводимая среда, защита от утечки тестов в обучающие данные. Публичный бенчмарк ≠ ваша задача — всегда стройте и свой набор.

🔷 10. Регрессионные наборы и трассы

  • Каждый найденный в проде сбой превращайте в тест-задачу
  • Версионируйте набор, промпты, модель и инструменты вместе
  • Запускайте набор в CI при смене промпта, модели или инструмента
  • Сравнивайте версии на одних и тех же задачах с повторами
import json, time, uuid

def log_step(trace, kind, **data):
    trace.append({"id": str(uuid.uuid4()),
                  "t": time.time(),
                  "kind": kind, **data})

trace = []
log_step(trace, "tool_call", name="search",
         args={"q": "курс"}, tokens=120)
log_step(trace, "tool_result", ok=True,
         latency_ms=340)
print(json.dumps(trace[0])[:60])

В трассах не храните секреты и персональные данные открытым текстом.

🔷 11. Плюсы и минусы

Плюсы систематической оценки:

  • Видно, действительно ли новая версия лучше
  • Ловит регрессии до выхода в прод
  • Позволяет искать ошибки по трассам
  • Связывает качество со стоимостью

Минусы:

  • Много прогонов — это деньги и время
  • Сложно писать надёжные оценщики
  • Судья-LLM смещён и тоже недетерминирован
  • Набор устаревает и «переобучается» под него

🔷 13. Типичные ошибки

  • ❌ Одна попытка на задачу — результат случаен
  • ❌ Усреднять pass@k и интерпретировать как надёжность
  • ❌ Судья не откалиброван на людях
  • ❌ Проверять только текст ответа, а не состояние среды
  • ❌ Подбирать промпт под тестовый набор и считать это итогом
  • ❌ Не логировать трассы — причины сбоев не найти
  • ❌ Сравнивать агентов без учёта стоимости
  • ❌ Выводы по малому набору без доверительного интервала
«Хороший агент — не тот, что один раз решил задачу, а тот, что решает её каждый раз и за разумную цену».

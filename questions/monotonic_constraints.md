# Monotonic constraints — вопросы для самопроверки

### Зачем накладывать монотонное ограничение, если модель и так хорошо предсказывает?
Чтобы прогноз соответствовал предметной логике (выше доход — не выше риск дефолта при прочих равных) и не давал абсурдных скачков в зонах с малым числом данных. Это повышает доверие, интерпретируемость и устойчивость при сдвиге данных, а также часто требуется регуляторами.

### Как задать монотонность в градиентном бустинге?
В XGBoost и LightGBM параметром `monotone_constraints` — вектор из 1 (возрастание), −1 (убывание), 0 (без ограничения) по каждому признаку; в sklearn `HistGradientBoostingRegressor` есть аналогичный параметр `monotonic_cst`. При построении дерева отбрасываются разбиения, нарушающие порядок значений в листьях.

### Монотонность по признаку означает «при прочих равных» или в данных?
При прочих равных: f(x₁, …, xⱼ + δ, …) ≥ f(x) для δ > 0 при фиксированных остальных признаках. В сырых данных зависимость может выглядеть немонотонной из-за корреляции с другими признаками — это не противоречие.

### Что будет, если навязать монотонность признаку, у которого реальная зависимость U-образная?
Модель будет вынуждена аппроксимировать её монотонной функцией (обычно «полкой» на одной из ветвей), и качество упадёт. Перед наложением ограничения стоит проверить зависимость через PDP/ICE и доменные знания.

### Как проверить, что обученная модель действительно монотонна?
Построить ICE-кривые для многих объектов, варьируя один признак при фиксированных остальных: все кривые должны быть неубывающими (или невозрастающими). Для бустинга с ограничением это гарантировано конструкцией, для постобработки или нейросетей — нужно проверять.

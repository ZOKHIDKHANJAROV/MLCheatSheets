# Gradient checkpointing — вопросы для самопроверки

### Какую проблему решает gradient checkpointing?
При обратном проходе нужны активации всех слоёв, и для глубоких моделей именно они занимают основную **память GPU**. Checkpointing сохраняет только часть активаций (контрольные точки), а остальные **пересчитывает** во время backward-прохода.

### Какой компромисс дают контрольные точки и какова классическая оценка?
Память меняется на вычисления: при n слоях и контрольных точках каждые √n слоёв память под активации снижается с O(n) до **O(√n)**, а цена — примерно один дополнительный прямой проход, то есть обучение замедляется ориентировочно на 20–40%.

### Что будет, если модель содержит dropout или другие случайные операции внутри checkpoint-сегмента?
При пересчёте сгенерировалась бы **другая маска** dropout, и градиенты не соответствовали бы прямому проходу. Поэтому реализации (например, `torch.utils.checkpoint.checkpoint`) по умолчанию сохраняют и восстанавливают состояние генератора случайных чисел.

### Где ставить контрольные точки в трансформере?
Обычно на границах **блоков** трансформера: сохраняется вход каждого блока, а всё внутри (attention, MLP) пересчитывается. В Hugging Face Transformers это включается `model.gradient_checkpointing_enable()`.

### Когда gradient checkpointing не нужен?
Если модель с нужным батчем и так помещается в память — он только замедлит обучение. Перед его включением стоит рассмотреть mixed precision, уменьшение батча с **gradient accumulation** и шардирование оптимизатора (ZeRO), которые экономят память иначе.

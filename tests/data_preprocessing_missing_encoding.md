# Предобработка данных: пропуски и кодирование — мини-тест

## Молодые клиенты реже указывают доход, и пропуски зависят от возраста, который известен. Какой это тип пропусков и как их разумно обработать?
- [ ] MCAR: пропуски случайны, поэтому подойдёт любое заполнение, даже константой 0
- [x] MAR: заполнять с учётом других признаков (`KNNImputer`, `IterativeImputer`)
- [ ] MNAR: пропуски зависят от самого дохода, поэтому заполнять нужно константой
- [ ] Это не пропуски, а выбросы, их следует удалить вместе с такими клиентами

**Почему.** Если вероятность пропуска зависит от другого наблюдаемого признака (возраста), это MAR, и значения разумно восстанавливать по похожим объектам. MCAR означает полную независимость, а MNAR — зависимость от самого пропущенного значения. Отличить MAR от MNAR по данным обычно нельзя, помогает знание предметной области.

## Доход известных клиентов: 52, 61, 1500, 48 (в тысячах), у остальных пропуск. Каким значением типично заполнить пропуски, если нужен устойчивый к выбросам вариант?
- [ ] 415.25, среднее по известным значениям
- [ ] 52, значение второго объекта в списке
- [x] 56.5, медиана известных значений
- [ ] 61, максимум без учёта выброса

**Почему.** Отсортированный ряд 48, 52, 61, 1500 имеет медиану (52 + 61) / 2 = 56.5. Среднее (52 + 61 + 1500 + 48) / 4 = 415.25 сильно сдвинуто выбросом 1500 и не похоже на типичный доход. Поэтому медиана — разумный выбор по умолчанию.

## Когда правильно вычислять медиану для заполнения пропусков, если данные нужно разбить на train и test?
- [x] Только по обучающей части, а затем применять эти значения и к test
- [ ] По всем данным до разбиения, чтобы значение было точнее
- [ ] Отдельно для train и для test, каждый по своим данным
- [ ] По test, так как именно в нём нужно заполнить пропуски

**Почему.** Статистики заполнения нужно учить только на train: иначе в обучение попадает информация о test (утечка). Правильный путь — `imputer.fit(X_train)`, затем `transform` для train и test; проще всего поместить импьютер в `Pipeline`. Раздельное заполнение по test делает преобразования train и test разными.

## Как правильно закодировать порядковый признак «размер одежды»: S, M, L, XL?
- [ ] `LabelEncoder` с порядком по умолчанию, так как он сохранит порядок размеров
- [ ] Frequency encoding: чем чаще встречается размер, тем он больше
- [ ] Хеширование в 8 столбцов, чтобы сохранить порядок через коллизии
- [x] `OrdinalEncoder` с явным порядком `categories=[["S", "M", "L", "XL"]]`

**Почему.** Для порядковых признаков нужна нумерация с заданным порядком: S → 0, M → 1, L → 2, XL → 3. По умолчанию категории сортируются по алфавиту (L, M, S, XL), и порядок размеров теряется. Частота и хеш к порядку величины отношения не имеют.

## Какие утверждения о пропусках и их обработке верны? (выберите все верные)
- [x] Скрытые пропуски вроде `-999` или `"unknown"` нужно сначала превратить в `NaN`
- [ ] Заполнение пропусков одной константой не ослабляет связи признака с остальными
- [x] LightGBM и XGBoost умеют работать с `NaN` сами, выбирая направление в каждом разбиении
- [ ] При MNAR пропуски можно просто удалить: смещения данных не возникнет

**Почему.** Если -999 оставить как есть, модель воспримет его как настоящее число. Бустинги обрабатывают `NaN` встроенным способом. Массовое заполнение константой сужает распределение и ослабляет связи, а при MNAR удаление или простое заполнение смещает данные, лучше добавить флаг пропуска (`add_indicator=True`).

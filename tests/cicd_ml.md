# CI/CD для ML — мини-тест

## Почему CI для ML-проекта не должен полностью обучать большую модель на каждый коммит?
- [ ] Потому что модель из CI нельзя сравнивать с продакшен-моделью
- [ ] Потому что CI-системы технически не умеют запускать обучение
- [x] Это долго и дорого, а CI достаточно проверить, что обучение работает
- [ ] Потому что полное обучение даёт менее точную модель, чем обучение на подвыборке

**Почему.** На коммит достаточно быстрых проверок: юнит-тестов, схемы данных, smoke-теста обучения на крошечной выборке. Тяжёлое обучение и оценку запускают реже: при слиянии в основную ветку или по расписанию. Сравнивать модели можно в любом случае, были бы одинаковые данные для оценки.

## Почему кандидата и продакшен-модель в quality gate сравнивают на одной и той же зафиксированной выборке?
- [x] Чтобы разница метрик отражала качество моделей, а не отличие данных
- [ ] Чтобы исключить утечку данных из обучающей выборки в валидационную
- [ ] Чтобы метрика считалась быстрее на заранее подготовленных данных
- [ ] Чтобы обе модели можно было вызвать через один и тот же API

**Почему.** Если модели оценены на разных данных, «улучшение» может объясняться более лёгкой выборкой, а не лучшей моделью. Фиксированная выборка делает сравнение честным, но от утечки сама по себе не защищает и на скорость расчёта почти не влияет.

## Что произойдёт при запуске этого кода?
```python
def quality_gate(f1, baseline_f1, min_gain=0.02):
    if f1 < baseline_f1 + min_gain:
        raise SystemExit("FAIL")
    print("OK")

quality_gate(0.715, baseline_f1=0.70)
```
- [ ] Выведется OK, потому что 0.715 больше 0.70
- [ ] Выведется OK, потому что прирост 0.015 положителен
- [ ] Произойдёт ошибка выполнения из-за сравнения чисел с плавающей точкой
- [x] Процесс завершится с FAIL, потому что порог равен 0.72

**Почему.** Порог = 0.70 + 0.02 = 0.72, а 0.715 < 0.72, поэтому выполняется `raise SystemExit`. Ненулевой код выхода останавливает конвейер CI. Одной положительной разницы недостаточно: gate требует прироста не меньше `min_gain`.

## Какой быстрый тест на каждый коммит выявит ошибку в коде обучения, если модель не умеет «переобучаться» на десятке объектов?
- [x] Проверка, что модель переобучается на маленькой выборке
- [ ] Сравнение метрики на валидации с метрикой продакшен-модели
- [ ] Проверка схемы входных данных на наличие нужных столбцов
- [ ] Тест API на отклонение некорректных запросов

**Почему.** Нормальная модель должна почти идеально выучить десяток объектов; если не получается, ошибка обычно в коде обучения (потеря, обновление весов, метки). Остальные проверки полезны, но проверяют другое: качество, данные или интерфейс сервиса.

## В `dvc.yaml` два этапа: `prepare` (зависит от `data/raw/train.csv` и `prepare.py`) и `train` (зависит от выхода `prepare`, `train.py` и параметра `train.learning_rate`). Вы изменили только `train.learning_rate` в параметрах. Что сделает `dvc repro`?
- [ ] Пересчитает оба этапа, так как параметры относятся ко всему пайплайну
- [ ] Ничего не пересчитает, потому что код не менялся
- [ ] Пересчитает только `prepare`, потому что он стоит первым в графе
- [x] Пересчитает только `train`, у которого изменился вход

**Почему.** `dvc repro` пересчитывает лишь этапы, у которых изменились зависимости (данные, код, параметры), поэтому результат `prepare` берётся из кэша. Параметр `train.learning_rate` указан именно у этапа `train`, а не у `prepare`.

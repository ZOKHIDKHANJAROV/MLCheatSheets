# RAG — мини-тест

## Зачем в RAG делают перекрытие (overlap) между соседними чанками?
- [ ] Перекрытие ускоряет поиск, потому что соседние чанки получают общие векторы эмбеддингов и их не нужно считать заново
- [x] Мысль на границе чанков не обрывается: она целиком попадает хотя бы в один из них
- [ ] Перекрытие уменьшает размер индекса, так как повторяющиеся слова хранятся в нём только один раз для всех чанков
- [ ] Перекрытие гарантирует, что каждый вопрос найдёт ровно один релевантный чанк и в результатах не будет дублей

**Почему.** Окно сдвигается с шагом size − overlap, поэтому текст на стыке повторяется в двух соседних чанках, и мысль не разрезается пополам. Эмбеддинги при этом считаются для каждого чанка отдельно, индекс из-за повторов растёт, а не уменьшается, и дубли в выдаче возможны.

## Для двух запросов первый релевантный документ стоит на 1-м и на 4-м месте. Чему равен MRR?
- [x] 0.625: среднее обратных рангов, то есть (1/1 + 1/4) / 2 = (1 + 0.25) / 2
- [ ] 0.4, потому что средний ранг равен 2.5, а MRR считается как 1 / (средний ранг)
- [ ] 0.25, потому что в MRR учитывается только худший из запросов, то есть ранг 4
- [ ] 0.5, так как 4-й результат считается ненайденным и даёт ноль: (1 + 0) / 2

**Почему.** MRR — среднее от обратных рангов первого релевантного результата: (1/1 + 1/4) / 2 = 0.625. Брать 1 / средний ранг нельзя (среднее считают по обратным величинам), худший запрос не выделяют, а ноль даёт только запрос, у которого релевантного результата в списке нет вовсе.

## Какие утверждения о гибридном поиске и реранкинге верны? (выберите все верные)
- [x] BM25 помогает находить редкие термины, коды ошибок и имена, которые плотный поиск часто пропускает
- [ ] Реранкер способен вернуть в выдачу чанк, которого не было среди кандидатов первого этапа, если он достаточно точный и мощный
- [x] RRF объединяет ранжирования суммой 1 / (k + rank), и веса для списков подбирать не требуется
- [ ] Гибридный поиск всегда точнее любого одного метода, поэтому метрики на собственных данных после его включения можно не проверять

**Почему.** BM25 опирается на точные слова, а RRF суммирует вклады рангов и не требует весов. Реранкер переупорядочивает только тех кандидатов, которых принёс первый этап. А выигрыш гибрида зависит от данных, поэтому recall@k и MRR всё равно нужно мерить.

## Нужный чанк попал в середину длинного контекста из 20 чанков, но модель ответила неверно. Что наиболее вероятно?
- [ ] BM25 не нашёл чанк из-за опечатки в запросе, поэтому в контексте его быть не могло, а ответ взят из параметров модели
- [ ] Чанк слишком мал: при вставке в prompt любой чанк автоматически обрезается до первых десяти токенов
- [ ] Реранкер всегда ухудшает порядок чанков, поэтому нужный чанк неизбежно оказывается в середине списка
- [x] Эффект «lost in the middle»: информацию из середины длинного контекста модель использует хуже

**Почему.** Чанк в контексте был, значит, поиск справился. Модели хуже используют середину длинного контекста, поэтому помогают меньший k и размещение важного по краям. Автоматической обрезки до десяти токенов нет, а реранкер не обязан портить порядок.

## Как правильно оценивать качество поисковой части RAG?
- [ ] Прочитать несколько ответов модели и оценить, нравятся ли они, ведь метрики поиска никак не связаны с качеством ответов
- [ ] Измерить перплексию модели генерации на документах базы знаний: она показывает, насколько полно поиск находит нужное
- [x] Взять вопросы с известными релевантными чанками и считать recall@k и MRR отдельно от генерации
- [ ] Сравнить размер индекса до и после чанкинга: чем меньше индекс получился, тем выше качество поиска

**Почему.** Retrieval оценивают отдельно: для вопросов с размеченными релевантными чанками считают recall@k, precision@k и MRR — так видно, что чинить, поиск или генерацию. Оценка «на глаз» не воспроизводима, перплексия и размер индекса о качестве поиска ничего не говорят.

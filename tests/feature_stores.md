# Feature stores — мини-тест

## Что такое training-serving skew и как с ним борется feature store?
- [ ] Это разница в размере обучающей и тестовой выборок; feature store её выравнивает, автоматически балансируя размеры при разбиении данных
- [ ] Это дрейф целевой переменной со временем; feature store автоматически переобучает модель на новых данных, как только дрейф обнаружен
- [x] Это расхождение значений признака при обучении и в онлайне; признаки считаются одним кодом для офлайн- и онлайн-хранилища
- [ ] Это медленное чтение признаков при инференсе; feature store ускоряет его сжатием таблиц и кэшированием признаков в памяти сервиса

**Почему.** Skew возникает, когда признак для обучения считали одним кодом (SQL по истории), а для онлайна — другим. Feature store хранит одно определение признака и наполняет им и офлайн-, и онлайн-хранилище, поэтому значения не расходятся. Дрейф целевой переменной — другая проблема.

## История значений признака `orders_30d` для пользователя: 3 января — 4, 7 января — 6, 12 января — 9. Метка (отток) относится к моменту 10 января. Какое значение признака даст point-in-time join?
- [ ] 4
- [x] 6
- [ ] 9
- [ ] 6.33

**Почему.** Point-in-time join берёт последнее значение, известное до момента метки: на 10 января это значение от 7 января, то есть 6. Значение 9 — последнее на сегодняшний день, но оно появилось позже метки, и его использование было бы утечкой из будущего; 6.33 — среднее, к join отношения не имеет.

## Что хранит онлайн-хранилище feature store и для чего оно нужно?
- [ ] Полную историю значений признаков за последние годы для сборки обучающей выборки на миллионы строк
- [ ] Определения признаков, их владельцев и способ расчёта, то есть реестр признаков с описанием источников данных
- [ ] Исходные сырые события в том виде, в котором они пришли из Kafka, для последующей переработки
- [x] Последнее значение признака для каждой сущности, отдаваемое за миллисекунды, обычно из Redis или DynamoDB

**Почему.** Онлайн-инференсу нужен быстрый доступ к актуальным значениям, поэтому там лежат только последние значения для каждой сущности (обычно в Redis или DynamoDB). Полная история хранится в офлайн-хранилище, а описания признаков — в реестре.

## В каких ситуациях feature store, скорее всего, окупается? (выберите все верные)
- [ ] Одна модель с пакетным скорингом, признаки считаются тем же SQL, что и при обучении
- [ ] Небольшой набор данных, а признаки дешевле каждый раз пересчитать с нуля
- [x] Десятки моделей разных команд переиспользуют одни и те же признаки
- [x] Онлайн-инференс с жёсткой задержкой и потоковыми признаками вроде «транзакций за 5 минут»

**Почему.** Feature store нужен при переиспользовании признаков многими моделями, онлайн-инференсе с требованиями к задержке и потоковых признаках. Для одной модели с пакетным инференсом он избыточен: инфраструктура сложнее самой задачи.

## Событие произошло в 10:00, но попало в хранилище признаков в 14:00. Почему при сборке обучающей выборки недостаточно знать только время события?
- [ ] Потому что офлайн-хранилище не умеет хранить время события, оно хранит только момент загрузки данных
- [x] Потому что в 12:00 значение ещё не было доступно, и его использование — утечка информации из будущего в обучение
- [ ] Потому что онлайн-хранилище хранит значения только с точностью до часа, а минуты и секунды отбрасывает
- [ ] Потому что TTL признака считается от времени попадания в хранилище, а не от времени события, и значение устаревает раньше

**Почему.** Честная выборка должна повторять то, что система знала в момент предсказания. Если значение появилось в хранилище в 14:00, использовать его для момента 12:00 нельзя, поэтому нужна и метка времени появления данных. Это отдельная ловушка помимо обычного join по последнему значению.

# PyTorch Lightning — мини-тест

## Обучение модели нужно перенести с ноутбука на CPU на сервер с 4 GPU. Что при использовании Lightning достаточно изменить?
- [ ] Переписать `training_step`, добавив `.to(device)` для каждого батча
- [x] Только аргументы `Trainer`: `accelerator`, `devices`, `strategy`
- [ ] Заменить `LightningModule` на обычный `nn.Module` с ручным циклом обучения
- [ ] Перенести оптимизатор из `configure_optimizers` в аргументы `Trainer`

**Почему.** `LightningModule` описывает, *что* обучать (модель, потери, шаги, оптимизатор), а `Trainer` отвечает за то, *как* это запускать: устройства, точность, стратегию. Поэтому один и тот же модуль работает на CPU и на нескольких GPU при смене аргументов `Trainer`. Ручной `.to(device)` внутри шагов не нужен и может мешать при нескольких GPU.

## Какие действия обычного цикла обучения PyTorch выполняет `Trainer` автоматически? (выберите все верные)
- [x] Вызовы `optimizer.zero_grad()` и `optimizer.step()`
- [ ] Выбор функции потерь, подходящей для задачи
- [x] Переключение модели в режим `eval()` на время валидации
- [ ] Определение архитектуры модели в `__init__`

**Почему.** В `training_step` достаточно вернуть потерю: `backward`, `zero_grad`, `step`, перенос на устройство и переключение `train`/`eval` берёт на себя `Trainer`. Функцию потерь и архитектуру выбирает пользователь — это «наука», а не рутина.

## DataLoader выдаёт батчи по 32 объекта, а у `Trainer` задано `accumulate_grad_batches=4`. Что получится на одном GPU?
- [ ] Эффективный батч равен 32, а память выросла в 4 раза
- [ ] Эффективный батч равен 128, а память выросла в 4 раза
- [ ] Эффективный батч равен 8 объектам, а память на шаг уменьшилась ровно в 4 раза
- [x] Эффективный батч равен 128, а память примерно как при батче 32

**Почему.** Градиенты суммируются по 4 мини-батчам, и только потом делается один шаг оптимизатора: 4 · 32 = 128. В памяти в каждый момент находится лишь один батч из 32 объектов, поэтому память не растёт.

## При запуске `Trainer(overfit_batches=1)` потеря не опускается почти до нуля, хотя модель должна легко запомнить один батч. Что это говорит?
- [ ] Модель слишком хорошо обучается, нужна более сильная регуляризация
- [ ] Это нормально: на одном батче потери не должны заметно падать
- [x] Скорее всего, есть ошибка в модели, функции потерь или данных
- [ ] Нужно включить `fast_dev_run`, чтобы модель прошла больше эпох

**Почему.** Один батч — самая простая задача для запоминания, поэтому правильно собранная модель должна довести потерю почти до нуля. Если этого нет, ищите баг (например, неверные метки или потери). `fast_dev_run` — это другая проверка: один батч обучения и валидации лишь для проверки, что код не падает.

## Почему ROC-AUC на валидации не стоит считать как среднее значений AUC по отдельным батчам?
- [ ] `self.log` умеет усреднять только функцию потерь, а значения любых других метрик логировать не умеет
- [x] AUC зависит от ранжирования по всей выборке, поэтому состояние копят, например в `torchmetrics`
- [ ] AUC нельзя вычислять на GPU, поэтому его считают по каждому батчу на CPU и усредняют
- [ ] AUC определён только для батчей, размер которых — степень двойки, иначе ранги считаются неверно

**Почему.** Метрики, которым нужны все предсказания сразу, нельзя получить усреднением по батчам: AUC каждого батча оценивает лишь ранжирование внутри него. `torchmetrics` накапливают предсказания по эпохе и считают значение корректно. Простые метрики вроде потери или точности `self.log` усредняет сам.

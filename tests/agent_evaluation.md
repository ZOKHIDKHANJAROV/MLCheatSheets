# Оценка агентов — мини-тест

## Служба поддержки с агентом должна решать каждое обращение без сбоев. Какая метрика лучше отражает такую надёжность?
- [ ] pass@k: чем больше попыток разрешено, тем ближе значение к единице, и это показывает, что агент стабилен
- [x] pass^k: вероятность того, что все k независимых попыток на задаче оказались успешными
- [ ] Доля задач, в которых агент хотя бы раз дал ответ, формально совпавший с эталоном по тексту
- [ ] Средняя длина трассы: чем короче траектория, тем надёжнее работает агент в эксплуатации

**Почему.** pass^k = C(c, k)/C(n, k) требует успеха во всех k попытках и убывает с ростом k, поэтому наказывает нестабильность. pass@k, наоборот, растёт с k и показывает лишь способность решить задачу хотя бы раз. Длина трассы говорит об эффективности, а не о надёжности.

## На задаче сделано n = 5 попыток, c = 4 успешны. Чему равна оценка pass^2 = C(c, k)/C(n, k)?
- [ ] 0,8
- [ ] 1,0
- [x] 0,6
- [ ] 0,64

**Почему.** C(4, 2)/C(5, 2) = 6/10 = 0,6. Значение 0,64 = 0,8² — это предел при истинной вероятности успеха 0,8, а несмещённая оценка по конечной выборке даёт 0,6. Единица была бы у pass@2, а 0,8 — это pass@1.

## Какие смещения характерны для LLM-as-a-judge? (выберите все верные)
- [x] Позиционное: при сравнении двух ответов судья склонен предпочитать вариант на определённом месте
- [ ] Судья не смещён, если рубрика написана без примеров, поскольку тогда он опирается только на общие знания
- [x] Склонность считать более длинный и подробный ответ лучшим независимо от его фактической верности
- [ ] Смещения исчезают при температуре 0, так как вердикт становится детерминированным и повторяемым

**Почему.** Позиционное смещение и предпочтение многословности — известные эффекты судей-LLM; их снижают обменом мест вариантов, чёткой рубрикой и калибровкой по оценкам людей. Температура 0 делает вердикт повторяемым, но не устраняет систематическую ошибку, а отсутствие примеров в рубрике смещения не убирает.

## Агент должен оформить возврат заказа через набор инструментов. Как надёжнее всего проверить успех задачи?
- [x] Сравнить состояние базы заказов после прогона с ожидаемым: статус, сумма, нет лишних правок
- [ ] Прочитать итоговое сообщение агента и убедиться, что в нём есть фраза «возврат оформлен» и вежливый тон
- [ ] Спросить другую LLM, насколько вежливо и уверенно агент сообщил пользователю о результате возврата
- [ ] Подсчитать число вызванных инструментов и сверить его с типичным числом шагов успешных запусков

**Почему.** Агент может написать «готово», ничего не сделав. Проверка итогового состояния среды объективна и ловит лишние побочные эффекты. Текст ответа и вердикт судьи о тоне не доказывают выполнение, а число шагов — это метрика траектории, не успеха.

## После очередного промпта агент перестал решать часть задач, которые раньше решал. Что поможет предотвратить повтор такого?
- [ ] Оценивать каждую новую версию только на нескольких заново придуманных удачных примерах из чата
- [ ] Перейти на публичный бенчмарк, потому что собственные тестовые задачи всегда менее надёжны
- [ ] Увеличить температуру до 1,0, чтобы повторные попытки с большей вероятностью давали успех
- [x] Собрать сбои из трасс в регрессионный набор и прогонять его с повторами при каждом изменении

**Почему.** Регрессионный набор из реальных сбоев с логами трасс и повторными прогонами сразу показывает, что сломалось. Несколько удачных примеров дают случайную картину, повышение температуры не лечит причину, а публичный бенчмарк (SWE-bench, GAIA, WebArena, τ-bench) не заменяет задач вашего продукта.

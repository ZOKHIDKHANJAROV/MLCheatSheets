# Мультиагентные системы — мини-тест

## В схеме supervisor один оркестратор и 5 исполнителей: он шлёт каждому задачу, и каждый отвечает. Сколько сообщений за один раунд?
- [ ] 5: считаются только задачи от оркестратора, а ответы исполнителей в раунд не входят
- [ ] 30: каждый из шести агентов отправляет сообщение каждому из пяти остальных агентов
- [x] 10: по одной задаче и одному ответу на каждого из пяти исполнителей
- [ ] 15: задача, ответ и ещё итоговое подтверждение для каждого исполнителя схемы

**Почему.** В supervisor число сообщений равно 2·k, где k — число исполнителей: 2·5 = 10. Схема «все-со-всеми» дала бы n·(n − 1) = 6·5 = 30, а отдельного подтверждения в описанной схеме нет.

## Что даёт исполнителю изолированный контекст по сравнению с общим?
- [x] Меньше токенов и меньше шума, но нужны явные передачи важных фактов от других агентов
- [ ] Более высокую согласованность, так как каждый исполнитель видит полную историю всех остальных агентов
- [ ] Гарантию отсутствия ошибок на стыках, потому что агенты вообще не обмениваются между собой информацией
- [ ] Ускорение за счёт того, что модель не читает промпт, а берёт готовый ответ из общей памяти

**Почему.** Изолированный контекст дешевле и сфокусированнее, но то, что исполнитель не получил явно, для него не существует. Полную историю видит агент с общим контекстом, а ошибки на стыках без явных передач, наоборот, вероятнее.

## В каких случаях лучше обойтись одним агентом? (выберите все верные)
- [ ] Подзадачи независимы, и их можно выполнять параллельно без обмена промежуточными результатами
- [x] Задача короткая, а её шаги жёстко следуют друг за другом
- [x] Нужен целиком общий контекст, например при правке одного файла
- [ ] Нужна независимая проверка результата вторым агентом с другой ролью и другими инструкциями

**Почему.** Короткая последовательная задача и работа с общим контекстом не выигрывают от разделения, а лишние сообщения стоят токенов. Независимые параллельные подзадачи и независимая проверка — как раз случаи, где несколько агентов могут помочь.

## Какая слабость есть у схемы debate, если все агенты работают на одной и той же модели?
- [ ] Судья обязательно должен быть человеком, иначе протокол просто не сможет завершиться
- [x] Агенты нередко повторяют общие ошибки одной модели, и дополнительные раунды их не исправляют
- [ ] Debate не работает на вопросах о фактах, потому что агенты не умеют ссылаться на источники
- [ ] Число сообщений растёт быстрее, чем у любой другой схемы, при любом числе агентов и раундов

**Почему.** Модель с одним и тем же заблуждением может убедить в нём всех участников спора. Помогает разнообразие ролей, моделей и источников. Судьёй может быть и модель, а число сообщений зависит от числа агентов и раундов: у «все-со-всеми» рост быстрее.

## Что обязательно предусмотреть в схеме handoff (swarm), где агенты передают управление друг другу?
- [ ] Единого оркестратора, который читает каждое сообщение, иначе передача управления между агентами невозможна
- [ ] Общую базу данных, где хранится весь контекст всех агентов целиком и без каких-либо сокращений
- [ ] Отдельного агента-судью, который голосованием определяет, кому передать управление на каждом шаге
- [x] Лимит числа передач, чтобы агенты не пересылали задачу друг другу по кругу бесконечно

**Почему.** В handoff центра нет, а значит, нет и того, кто остановит бесконечную пересылку: нужен лимит передач и условие завершения. Единый оркестратор, общая база и судья — не обязательные элементы этого паттерна.

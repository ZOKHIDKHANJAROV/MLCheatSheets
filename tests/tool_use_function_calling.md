# Вызов инструментов (function calling) — мини-тест

## Что происходит, когда модель «вызывает функцию» при function calling?
- [ ] Модель исполняет код функции внутри себя и сразу подставляет результат в ответ пользователю
- [x] Модель возвращает имя функции и аргументы в JSON, а вызывает её приложение
- [ ] Модель напрямую обращается к внешнему API по сети, минуя ваше приложение и его проверки
- [ ] Модель дообучается на описании функции и запоминает её результат для будущих запросов

**Почему.** Модель лишь формирует структурированный запрос (имя, аргументы, id). Выполнение, проверка аргументов и безопасность — на стороне приложения; веса модели при этом не меняются.

## Модель вернула вызов get_weather с аргументами {"town": "Казань"}, а в схеме обязательное поле называется city. Как правильно поступить?
- [ ] Молча подставить значение town в параметр city и выполнить функцию, чтобы не тратить лишний шаг модели
- [ ] Завершить весь цикл агента исключением, поскольку модель нарушила схему и дальше работать не может
- [x] Не выполнять функцию и вернуть модели ошибку: нет поля city, лишнее поле town
- [ ] Выполнить функцию с пустым city и вернуть результат так, как будто вызов прошёл успешно

**Почему.** Аргументы от модели — недоверенный ввод, их проверяют по схеме до выполнения. Понятная ошибка в tool_result позволяет модели исправить вызов. Молчаливые подстановки и «успешный» ответ на неверный вызов скрывают проблему.

## Какие утверждения о параллельных вызовах верны? (выберите все верные)
- [x] Модель может вернуть несколько вызовов за один ход; независимые можно запускать одновременно
- [ ] Идентификатор вызова не нужен: результаты сопоставляются с вызовами строго по порядку получения
- [x] Каждый результат возвращают со своим tool_call_id, чтобы его можно было сопоставить с вызовом
- [ ] Вызовы, где аргументы второго зависят от результата первого, тоже безопасно запускать одновременно

**Почему.** Независимые вызовы (погода в двух городах) выполняются одновременно, а результаты привязываются к вызовам по id — порядок завершения может отличаться. Зависимые вызовы идут по очереди: аргументы второго появляются только после результата первого.

## Зачем в цикле вызова инструментов задают max_steps?
- [ ] Чтобы ускорить ответ модели: чем меньше шагов разрешено, тем быстрее генерируется каждый токен
- [ ] Чтобы модель не могла вызывать инструменты чаще одного раза за диалог, ведь повторные вызовы запрещены
- [ ] Чтобы автоматически проверять аргументы функций по JSON-схеме перед каждым вызовом
- [x] Чтобы цикл не шёл бесконечно, если модель повторяет вызов и не приходит к ответу

**Почему.** max_steps — предохранитель от зацикливания и лишних расходов. На скорость генерации токенов он не влияет, повторные вызовы допустимы, а проверка аргументов — отдельный механизм (валидация по схеме).

## Инструмент выбросил исключение: внешний сервис недоступен. Какая реакция наиболее разумна?
- [ ] Ничего не добавлять в историю и повторно вызвать модель с теми же сообщениями, надеясь на другой ответ
- [x] Перехватить исключение и вернуть модели tool_result с описанием ошибки
- [ ] Подставить в tool_result правдоподобное значение по умолчанию, чтобы цикл завершился без ошибок и выглядел успешным
- [ ] Остановить всё приложение и показать пользователю трассировку стека целиком, не продолжая диалог

**Почему.** Ошибка инструмента — тоже наблюдение: получив её описание, модель может повторить вызов с другими аргументами, выбрать другой инструмент или честно сообщить о сбое. Выдуманное значение вводит в заблуждение, а «глухое» повторение или падение приложения ничего не исправляют.

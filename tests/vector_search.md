# Векторный поиск — мини-тест

## Векторы нормализованы до единичной длины. Что верно про косинус, скалярное произведение и L2?
- [ ] Скалярное произведение даёт порядок, обратный косинусу, потому что нормализация меняет знак у всех значений сходства
- [x] Порядок соседей одинаков для всех мер, ведь ‖a − b‖² = 2 − 2·cos(a, b) и cos(a, b) = a·b
- [ ] У L2 порядок отличается от косинусного, так как расстояние зависит от длин векторов, а они после нормализации разные
- [ ] Порядок совпадает только для первого соседа, а для остальных позиций меры расходятся из-за ошибок округления

**Почему.** При ‖a‖ = ‖b‖ = 1 квадрат расстояния связан с косинусом убывающей линейной формулой, а косинус равен скалярному произведению, поэтому сортировка по любой из мер даёт один и тот же порядок. После нормализации длины у всех равны единице, а не «разные».

## Вектор из 128 чисел float32 сжимают product quantization: m = 8 подвекторов, по 256 центроидов в словаре. Во сколько раз он станет меньше (словари не считаем)?
- [ ] В 16 раз: каждое число float32 заменяется двухбайтовым кодом после квантования значений
- [ ] В 8 раз: по одному байту хранится каждый из 8 подвекторов, а остальные байты вектора остаются
- [ ] В 32 раза: вместо 4 байт на число остаётся 1 бит, как в бинарном хэшировании векторов
- [x] В 64 раза: исходные 512 байт превращаются в 8 байт, по одному байту на каждый подвектор

**Почему.** Исходный вектор занимает 128 · 4 = 512 байт. Каждый подвектор заменяется номером из 256 центроидов — это один байт, итого 8 байт: 512 / 8 = 64. Остальных «оставшихся» байт нет, а PQ — не побитовое хэширование.

## Какие утверждения об индексе IVF верны? (выберите все верные)
- [x] При nprobe = nlist просматриваются все ячейки, и результат совпадает с точным перебором
- [ ] Рост nprobe сокращает число просматриваемых векторов, поэтому поиск ускоряется, а recall остаётся неизменным
- [x] Если ближайший сосед запроса лежит в непросмотренной ячейке, индекс его не найдёт
- [ ] Ячейки получаются случайным разбиением без учёта близости векторов, а центроиды нужны только для сжатия данных

**Почему.** Ячейки строит k-means, а nprobe — число просматриваемых ячеек: при nprobe = nlist это перебор всей базы, при малом nprobe сосед из соседней ячейки теряется. Рост nprobe, наоборот, увеличивает число сравнений и замедляет поиск, повышая recall.

## Как измеряют качество приближённого индекса?
- [ ] Сравнивают время запроса с точным перебором: чем быстрее индекс, тем выше его качество поиска
- [ ] Считают среднюю длину векторов до и после построения индекса: она не должна заметно меняться
- [x] Считают recall@k: доля точных top-k соседей, найденных индексом, на реальных запросах
- [ ] Проверяют, что для каждого запроса индекс возвращает ровно k результатов независимо от их близости

**Почему.** Эталоном служит точный перебор: recall@k = |ANN-top-k ∩ точный top-k| / k. Скорость показывает другую сторону компромисса, а не качество, длина векторов к нему не относится, а число возвращённых результатов не говорит об их правильности.

## Под фильтр по метаданным подходит лишь 0.5% базы, а поиск идёт с пост-фильтрацией при k = 10. Что может случиться?
- [ ] Индекс автоматически перестроится под фильтр, и результат станет полностью точным без дополнительных затрат времени
- [x] Среди найденных top-10 может не оказаться подходящих записей: результат будет пустым или короче k
- [ ] Запрос завершится ошибкой, потому что фильтр можно применять только до обращения к индексу
- [ ] Все десять результатов гарантированно подойдут под фильтр, так как индекс заранее отсортировал записи по метаданным

**Почему.** Пост-фильтр сначала берёт top-k по близости и лишь потом отбрасывает неподходящее; при узком фильтре почти все найденные записи отсеиваются. Выход — запас по k, пре-фильтр или точный перебор по отобранным записям. Автоматической перестройки индекса при этом не происходит.

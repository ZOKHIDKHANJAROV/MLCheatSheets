# Production ML Best Practices — мини-тест

## Бизнесу достаточно, чтобы рекомендации «на завтра» для всей клиентской базы обновлялись раз в сутки. Какой способ развёртывания разумнее выбрать?
- [ ] Online API с ответом за десятки миллисекунд на каждый запрос клиентского приложения
- [ ] Streaming через Kafka с реакцией на каждое событие и онлайн-обновлением признаков
- [x] Batch: ночной пересчёт предсказаний для всех объектов с записью в таблицу
- [ ] Edge: запуск модели на смартфонах и других устройствах пользователей

**Почему.** Нужно выбирать самый простой способ, который решает задачу: пакетный скоринг гораздо проще поддерживать, чем онлайн-сервис с жёсткими требованиями по задержке. Online и streaming оправданы, когда ответ нужен сразу (антифрод при оплате), а edge — для работы на устройстве и приватности.

## При обучении средний чек клиента считали в SQL по закрытым дням, а в сервисе реализовали отдельно на Python по текущему дню. Как называется возникшая проблема и чем её лечат?
- [ ] Concept drift; лечится периодическим дообучением на свежих данных без изменения кода признаков
- [ ] Утечка данных; лечится увеличением тестовой выборки и повторной оценкой качества на ней
- [ ] Переобучение; лечится регуляризацией, ранней остановкой и уменьшением сложности модели
- [x] Training-serving skew; лечится единым кодом признаков и сохранением предобработки с моделью

**Почему.** Признаки при обучении и в бою считаются по-разному, поэтому модель получает «не те» числа и деградирует без единой ошибки в логах. Защита: один и тот же код для обучения и инференса, сохранение `Pipeline` целиком, логирование признаков и сравнение их распределений с обучающими.

## Новую модель нужно проверить на живом трафике так, чтобы она предсказывала параллельно с текущей, но ни одно решение по её ответам не принималось. Как называется этот режим?
- [ ] Canary
- [x] Shadow
- [ ] A/B-тест
- [ ] Batch

**Почему.** В shadow-режиме модель получает реальные запросы и считает предсказания, но на пользователей не влияет, так что её можно сравнить с работающей. Canary уже отдаёт ответы небольшой доле пользователей, а в A/B-тесте решения по разным моделям принимаются для разных групп.

## Почему хорошая метрика на отложенной выборке не гарантирует успеха в продакшене? (выберите все верные)
- [x] Данные в бою приходят из другого периода или от другой аудитории
- [ ] ROC-AUC нельзя вычислять на данных, не участвовавших в обучении
- [x] Рекомендации меняют поведение пользователей, поэтому будущие данные зависят от самой модели
- [ ] Отложенная выборка по определению содержит больше шума, чем обучающая

**Почему.** Сдвиг данных и feedback loop делают офлайн-оценку нерепрезентативной, а бизнес-метрика (выручка, конверсия) к ML-метрике привязана не напрямую. ROC-AUC как раз считают на отложенных данных, а различие в шуме между выборками отношения к проблеме не имеет.

## Зачем перед выкаткой сложной модели нужен бейзлайн — константа, бизнес-правило или логистическая регрессия?
- [ ] Чтобы заменить им A/B-тест новой модели и не тратить время на живой трафик
- [ ] Чтобы использовать его веса как начальную инициализацию сложной модели при дообучении
- [ ] Чтобы доказать, что сложная модель не переобучена и не запоминает выборку
- [x] Чтобы понять, окупает ли ML затраты, и получить точку отсчёта для мониторинга

**Почему.** Простое разумное решение показывает, насколько сложная модель реально лучше, и служит запасным значением и ориентиром при мониторинге деградации. Он не заменяет проверку на живом трафике и сам по себе не говорит о переобучении.

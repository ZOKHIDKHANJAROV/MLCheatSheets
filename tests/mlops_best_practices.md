# MLOps Best Practices — мини-тест

## Модель в продакшене стала хуже предсказывать, хотя код сервиса и обучения никто не менял. Какая причина наиболее вероятна с точки зрения MLOps?
- [ ] Обученные веса модели со временем «изнашиваются» при хранении на диске, и числа в файле портятся
- [x] Изменились входные данные: поведение системы определяют код, данные и сама обученная модель
- [ ] Модель перестала работать, потому что в Git давно не было коммитов и CI-пайплайн отключил сервис
- [ ] Реестр моделей без ведома команды автоматически подменил веса на более старую версию из архива

**Почему.** В ML поведение системы задают код, данные и модель. Распределение данных в продакшене меняется (дрейф), поэтому модель портится без единого изменения кода. Для этого и нужны мониторинг данных и качества, версионирование данных и переобучение.

## Чем shadow deployment отличается от canary release?
- [x] Shadow получает копию трафика, ответы не отдаются; canary обслуживает малую долю реального трафика
- [ ] Shadow-режим означает полную замену старой модели новой на всём трафике, а canary — откат на прежнюю версию
- [ ] В shadow-режиме новая модель отвечает пользователям вместо старой, а в canary — только пишет логи без ответов
- [ ] Это одно и то же, разница только в названии у разных облачных провайдеров и платформ

**Почему.** Shadow ловит технические проблемы (ошибки, задержки, странные распределения прогнозов) без риска для пользователей: решения принимает старая модель. Canary уже влияет на реальных пользователей, но малой долей, например 5 %, и модель можно быстро выключить.

## Как DVC версионирует большие датасеты?
- [ ] Хранит сами данные прямо в Git-репозитории, но в сжатом виде, поэтому коммиты занимают меньше места
- [ ] Хранит только метрики, полученные на датасете, а сами данные удаляет после завершения обучения модели
- [x] Хранит в Git небольшой файл-указатель (`dataset.csv.dvc`), а сами данные — во внешнем хранилище
- [ ] Версионирует только код обучения и конфигурации, а данные считаются неизменными и отдельно не хранятся

**Почему.** Данные слишком велики для Git, поэтому в коммит попадает указатель, а `dvc push` отправляет данные в облачное хранилище. Так один коммит однозначно определяет и код, и версию данных, на которых обучена модель.

## Мониторинг сообщил о дрейфе, и пайплайн автоматически переобучил модель на свежих данных. Что нужно сделать перед выкаткой переобученной модели?
- [ ] Ничего: модель обучена на свежих данных, значит она не хуже текущей, и проверка только задержит выкатку
- [x] Сравнить с текущей моделью на одной свежей выборке и выкатывать только после прохождения quality gate
- [ ] Сразу выкатить на 100 % трафика, чтобы как можно быстрее исправить ситуацию с дрейфом и не терять качество
- [ ] Удалить из реестра прежнюю модель из продакшена, чтобы в реестре не было путаницы между версиями

**Почему.** Новая модель может оказаться хуже, например из-за ошибки разметки в свежих данных. Quality gate — автоматическая проверка на одной и той же выборке, по которой решают, можно ли выпускать модель. Старую версию в реестре нужно сохранить для отката.

## Какие утверждения верны? (выберите все верные)
- [ ] Нулевой уровень зрелости MLOps — это когда пайплайн обучения автоматически запускается по расписанию
- [x] Сервис может отвечать быстро и без ошибок, но выдавать неверные предсказания, поэтому мониторят данные и качество, а не только инфраструктуру
- [ ] Реестр моделей нужен для хранения сырых обучающих данных вместо DVC
- [x] Без версии данных эксперимент, даже при сохранённом коммите кода, может оказаться невоспроизводимым

**Почему.** Автоматизация обучения по расписанию — это уже первый уровень, а нулевой — ручная работа в ноутбуках. Реестр хранит версии и статусы моделей, а данные версионируют отдельно (DVC). Метрики инфраструктуры (задержка, ошибки) не видят деградации качества.

# Кодирование категориальных признаков — мини-тест

## Почему ordinal-кодирование номинального признака «город» (c0, c1, …, c49) вредит логистической регрессии?
- [ ] Ordinal-кодирование удаляет из данных информацию о том, какие именно города встречались
- [x] Модель ищет один общий наклон по номерам, а порядка у городов нет
- [ ] Ordinal-кодирование создаёт столько же столбцов, сколько городов, и модель переобучается
- [ ] Логистическая регрессия не принимает на входе целые числа, только вещественные

**Почему.** Линейная модель воспринимает код как величину: c40 для неё «больше» c3, и она ищет одну прямую по номерам. Если номера не связаны с эффектом города, качество близко к случайному (в примере лекции ROC-AUC ≈ 0.51). Столбцов при ordinal-кодировании как раз остаётся один, а целые числа модель принимает без проблем.

## Какая главная опасность target encoding, если считать среднее цели по категории на всей выборке?
- [ ] Число столбцов растёт пропорционально числу категорий, и матрица становится разреженной
- [ ] Редкие категории вообще не получают числового значения, и объекты приходится удалять
- [ ] Результат зависит от алфавитного порядка категорий, и модель выучит ложный порядок
- [x] Для редкой категории среднее почти равно собственной цели объекта: утечка

**Почему.** Если в категории один-два объекта, её «среднее цели» фактически содержит ответ для самого объекта, и модель переобучается. Защита: сглаживание средним по всей выборке и подсчёт по фолдам (так делает `TargetEncoder` в scikit-learn). Target encoding даёт один столбец, а не по столбцу на категорию.

## Что выведет код?
```python
from sklearn.preprocessing import OrdinalEncoder

enc = OrdinalEncoder(categories=[["S", "M", "L", "XL"]])
print(enc.fit_transform([["L"], ["S"], ["XL"]]).ravel())
```
- [x] [2. 0. 3.]
- [ ] [1. 0. 2.]
- [ ] [0. 1. 2.]
- [ ] [3. 0. 2.]

**Почему.** Порядок задан явно: S → 0, M → 1, L → 2, XL → 3, поэтому L, S, XL кодируются как 2, 0, 3. Позиции в выходе соответствуют порядку строк входа. Без параметра `categories` категории отсортировались бы по алфавиту (L, S, XL → 0, 1, 2) и порядок размеров потерялся бы.

## Признак «ID товара» принимает около 50 000 значений. Какие подходы к нему подходят? (выберите все верные)
- [ ] One-hot с `drop="first"`: удаление одного столбца решает проблему размерности
- [x] Target encoding со сглаживанием и подсчётом по фолдам
- [ ] `LabelEncoder` на признаке, чтобы получить один столбец без потерь для линейной модели
- [x] Хеширование (`FeatureHasher`) в фиксированное число столбцов ценой коллизий

**Почему.** Target encoding и хеширование дают компактное представление высококардинальных признаков, при этом хеширование допускает коллизии. `drop="first"` убирает лишь один столбец из 50 000, а `LabelEncoder` предназначен для целевой переменной и, как любое числовое кодирование номинального признака, вводит ложный порядок.

## Вы кодируете признак командой `pd.get_dummies` отдельно для train и для test. В чём риск?
- [ ] Столбцы test окажутся закодированы по среднему значению цели из обучающей выборки
- [ ] Категории test автоматически объединятся с редкими категориями из обучающей выборки
- [x] Наборы столбцов могут различаться, а новые категории не обработаются
- [ ] Столбцы test будут упорядочены по частоте категорий в обучающей выборке

**Почему.** `get_dummies` не запоминает категории: если в test нет какого-то значения или есть новое, столбцы не совпадут с теми, на которых училась модель. Правильно использовать кодировщик scikit-learn, обученный на train и встроенный в пайплайн, например `OneHotEncoder(handle_unknown="ignore")`. Утечки цели здесь нет: `get_dummies` целевую переменную не использует.

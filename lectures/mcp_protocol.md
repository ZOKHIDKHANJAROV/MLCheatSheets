# Model Context Protocol (MCP)

<!-- время: 15 мин -->

> **О чём лекция.** Зачем понадобился общий стандарт подключения инструментов к ИИ-приложениям, как устроены клиент и сервер MCP, какие три вида возможностей сервер может предложить и почему безопасность остаётся вашей заботой.

## Зачем это нужно

Чтобы ИИ-ассистент был полезен, ему нужен доступ к вашим данным и инструментам: файлам, базам, трекеру задач, почте. До появления общих стандартов каждое приложение писало собственные коннекторы к каждой системе. Если приложений N, а систем M, то коннекторов нужно N × M, и каждый приходится поддерживать отдельно. Добавили новую систему — пишем N новых коннекторов.

Model Context Protocol (MCP) — открытый протокол, который представила компания Anthropic в конце 2024 года. Идея проста: стороны один раз договариваются о формате общения. Приложение реализует *клиент*, система — *сервер*, и любой клиент работает с любым сервером. Вместо N × M реализаций получается N + M.

## Интуиция: единый разъём

Вспомните USB. Раньше у каждой техники был свой штекер и свой провод. Единый разъём не делает флешку умнее, но избавляет от пучка переходников: достаточно, чтобы обе стороны поддерживали стандарт. MCP — такой же разъём между ИИ-приложением и внешним миром.

- **Host** — приложение с моделью (чат, редактор кода, агент).
- **Клиент** — модуль внутри host, который держит соединение с одним сервером.
- **Сервер** — программа, которая выставляет наружу возможности: файлы, запросы к базе, вызовы API.
- **Протокол** — правила обмена сообщениями между клиентом и сервером.

## Как это работает

**Архитектура.** Host может содержать несколько клиентов, каждый подключён к своему серверу. Решения о том, что и когда вызывать, принимает host вместе с моделью; сервер сам модели не звонит, он только отвечает на запросы.

**Три типа возможностей сервера.**

| тип | что это | кто решает использовать |
|---|---|---|
| Tools | функции, которые что-то делают: поиск, запись, запрос | модель |
| Resources | данные для контекста: файлы, записи, документы | приложение |
| Prompts | готовые шаблоны запросов, часто с параметрами | пользователь |

Кроме того, клиент может предоставлять серверу собственные возможности, например запросить у модели продолжение текста (sampling).

**Транспорты.** Для обмена сообщениями есть два основных способа:

- *stdio* — host запускает сервер как дочерний процесс, сообщения идут через стандартные ввод и вывод. Просто, локально, без сети;
- *HTTP* — сервер доступен по сети, запросы клиента идут по HTTP, а ответы и уведомления могут приходить потоком. Подходит для удалённых серверов, но требует аутентификации.

Формат сообщений от транспорта не зависит.

**Обмен сообщениями JSON-RPC.** MCP использует JSON-RPC 2.0. Существует три вида сообщений:

- *запрос* — содержит `method` и `id`, ждёт ответа;
- *ответ* — содержит тот же `id` и либо `result`, либо `error` (с полями `code` и `message`);
- *уведомление* — содержит `method`, но не содержит `id`; ответа не ждёт.

Ответ связывают с запросом по `id`. Номера выдаёт каждая сторона независимо, поэтому запрос клиента с `id = 1` и запрос сервера с `id = 1` — разные запросы.

**Жизненный цикл.** Клиент отправляет запрос `initialize`, в котором стороны согласуют версию протокола и возможности. Сервер отвечает, клиент присылает уведомление `notifications/initialized`. После этого клиент может запрашивать каталог (`tools/list`, `resources/list`, `prompts/list`) и вызывать возможности (`tools/call`, `resources/read`, `prompts/get`).

**Права и безопасность.** Протокол описывает обмен, но не делает его безопасным сам по себе. Сервер — это стороннее ПО с доступом к вашим данным. Поэтому: подключайте только доверенные серверы, давайте минимальные права, требуйте подтверждения пользователя для опасных действий (запись, удаление, отправка), проверяйте аргументы вызова, ограничивайте объём ответа и ставьте таймауты. Результат инструмента — это *данные*, а не команда: в тексте ответа может быть внедрённая инструкция (prompt injection).

## Пример на Python

Здесь нет ни сети, ни готовых библиотек MCP: учебный «сервер» — функция, обрабатывающая сообщения JSON-RPC, а «клиент» — несколько вызовов. Это схема обмена, а не реализация протокола.

```python
import json

TOOLS = {"echo": lambda args: args.get("text", "")}


def handle(line):
    """Обрабатывает одно сообщение JSON-RPC и возвращает ответ (или None)."""
    msg = json.loads(line)
    if "id" not in msg:                       # уведомление: ответа нет
        return None
    if msg["method"] == "tools/list":
        result = {"tools": [{"name": name} for name in TOOLS]}
    elif msg["method"] == "tools/call":
        params = msg["params"]
        text = TOOLS[params["name"]](params["arguments"])
        result = {"content": [{"type": "text", "text": text}]}
    else:
        error = {"code": -32601, "message": "метод не найден"}
        return json.dumps({"jsonrpc": "2.0", "id": msg["id"], "error": error})
    return json.dumps({"jsonrpc": "2.0", "id": msg["id"], "result": result})


requests = [
    {"jsonrpc": "2.0", "method": "notifications/initialized"},
    {"jsonrpc": "2.0", "id": 1, "method": "tools/list"},
    {"jsonrpc": "2.0", "id": 2, "method": "tools/call",
     "params": {"name": "echo", "arguments": {"text": "привет"}}},
    {"jsonrpc": "2.0", "id": 3, "method": "unknown/method"},
]
for request in requests:
    reply = handle(json.dumps(request))
    print(request.get("id"), "->", reply)
```

Обратите внимание, что на уведомление ответа нет, а ответ на неизвестный метод — это `error`, а не исключение: клиент всегда узнаёт, чем закончился запрос.

## Подводные камни

- **Слишком много инструментов.** Описание каждого инструмента попадает в контекст модели; когда их десятки, контекст раздувается и модель чаще выбирает не тот.
- **Слепое доверие серверу.** Сервер выполняет код и видит то, что вы ему передали. Подключайте проверенные серверы и ограничивайте права.
- **Prompt injection через результаты.** Текст из внешнего источника может содержать команды для модели. Относитесь к нему как к данным и подтверждайте опасные действия.
- **Ожидание ответа на уведомление.** У уведомления нет `id`, ответ не придёт; ждать его — значит получить зависание.
- **Нет таймаутов.** Вызов инструмента может не завершиться. В протоколе таймаут не вшит — его задаёт клиент.
- **Секреты в описаниях.** Описания инструментов видны модели; не кладите туда пароли и ключи.
- **Путаница `result` и `error`.** Ответ содержит либо одно, либо другое: проверяйте, какое поле пришло.

## Итоги

- MCP — открытый протокол подключения внешних инструментов и данных к ИИ-приложениям; он превращает N × M интеграций в N + M.
- Архитектура: host, клиенты внутри него и серверы; решения о вызовах принимает host.
- Сервер предоставляет tools (действия), resources (данные) и prompts (шаблоны).
- Транспорты — stdio для локальных серверов и HTTP для удалённых; формат сообщений общий — JSON-RPC 2.0.
- Ответ сопоставляется с запросом по `id`; у уведомления `id` нет.
- Безопасность — ваша забота: доверенные серверы, минимальные права, подтверждения, таймауты.

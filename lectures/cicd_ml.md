# CI/CD для ML

<!-- время: 15 мин -->

> **О чём лекция.** Как автоматически проверять и выкатывать ML-системы: чем CI/CD для моделей отличается от обычного, какие тесты запускать на каждый коммит, что такое quality gate и как сделать сборку модели воспроизводимой.

## Зачем это нужно

В обычной разработке давно принято: каждый коммит автоматически собирается и проходит тесты (**CI**, continuous integration), а прошедшая проверки версия автоматически выкатывается на тестовый или боевой сервер (**CD**, continuous delivery или deployment). Это ловит ошибки до того, как они дойдут до пользователей, и делает выкатку рутинной операцией, а не ночным приключением.

ML-проект — тоже код, и всё это к нему применимо. Но в ML ломаться могут ещё данные и модель. Тесты кода проходят, а новая модель на 5% хуже старой. Или данные пришли с новым столбцом, и обучение молча использовало мусор. Поэтому CI/CD для ML расширяют проверками данных и моделей, а к CI и CD добавляют **CT** — continuous training, автоматическое переобучение.

## Интуиция: три шлагбаума

Изменение по пути в продакшен проходит три шлагбаума:

1. **Код корректен** — линтеры и юнит-тесты.
2. **Данные корректны** — схема, диапазоны, пропуски, объём.
3. **Модель не хуже текущей** — метрики на зафиксированной валидационной выборке выше порога.

Если любой шлагбаум закрыт, изменение не идёт дальше. Последний шлагбаум и называют **quality gate**.

## Как это работает: чем ML отличается от обычного CI/CD

| | обычное приложение | ML-система |
|---|---|---|
| что версионируется | код | код, данные, модели, параметры |
| что тестируется | логика кода | код, данные, качество модели |
| результат сборки | детерминированный бинарник | модель, которая зависит от данных и случайности |
| время сборки | минуты | обучение может идти часами |
| когда пересобирать | при изменении кода | ещё и при изменении данных или по расписанию |

## Какие тесты запускать

**На каждый коммит** — быстрые проверки, укладывающиеся в минуты:

- юнит-тесты функций предобработки и признаков: на маленьком примере результат известен заранее;
- тесты схемы данных: нужные столбцы есть, типы верные, значения в разумных диапазонах;
- **smoke-тест обучения**: модель обучается на крошечной выборке за секунды и предсказывает массив правильной формы без NaN;
- проверка, что модель может **переобучиться** на десятке объектов: если не может, в коде обучения ошибка;
- тесты API: сервис принимает корректный запрос и отклоняет некорректный.

**При слиянии в основную ветку или по расписанию** — тяжёлые этапы: полное обучение, оценка на отложенной выборке, сравнение с моделью в продакшене, регистрация новой версии.

Полностью обучать большую модель на каждый коммит невыгодно: это дорого, долго и блокирует разработчиков. Поэтому CI проверяет, что обучение *работает*, а полное обучение запускают реже.

## Quality gate

Quality gate — автоматическое правило, которое пропускает модель дальше только при выполнении условий:

- основная метрика не хуже текущей продакшен-модели (часто с запасом, например +0.5 п.п.);
- метрика выше бейзлайна;
- по важным сегментам (регионам, группам пользователей) нет заметной деградации;
- задержка инференса и размер модели в допустимых пределах.

Важно, чтобы модели сравнивались на **одной и той же** зафиксированной выборке: иначе разница метрик может объясняться разными данными, а не качеством.

## Воспроизводимость

Чтобы пайплайн обучения в CI давал предсказуемый результат:

- фиксируйте версии зависимостей (`requirements.txt` с точными версиями или lock-файл) и собирайте в Docker-образе;
- фиксируйте `random_state` и seed во всех библиотеках;
- версионируйте данные (DVC) и параметры (`params.yaml`);
- описывайте пайплайн как граф этапов — например, в `dvc.yaml`: `dvc repro` пересчитывает только этапы, у которых изменились входы.

```
stages:
  prepare:
    cmd: python prepare.py
    deps: [data/raw/train.csv, prepare.py]
    outs: [data/processed/train.csv]
  train:
    cmd: python train.py
    deps: [data/processed/train.csv, train.py]
    params: [train.learning_rate]
    metrics: [metrics.json]
    outs: [models/model.pkl]
```

## Как выглядит конвейер

Конфигурация CI — это файл со списком шагов. Пример в синтаксисе GitHub Actions (у GitLab CI и других систем идея та же):

```
name: ml-pipeline
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: pytest tests/                 # юнит-тесты и smoke-тест обучения
      - run: python scripts/validate_data.py
      - run: python train.py --sample 0.05  # быстрое обучение на подвыборке
      - run: python scripts/quality_gate.py # сравнение с порогом
```

Шаг с ненулевым кодом выхода останавливает весь конвейер. Именно так quality gate «закрывает шлагбаум».

## Пример на Python

Quality gate как функция: сравниваем кандидата с бейзлайном и завершаем процесс с ошибкой, если прирост недостаточен.

```python
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.dummy import DummyClassifier
from sklearn.metrics import f1_score

def quality_gate(model, X_val, y_val, baseline_f1, min_gain=0.02):
    f1 = f1_score(y_val, model.predict(X_val))
    if f1 < baseline_f1 + min_gain:
        raise SystemExit(f"FAIL: F1 {f1:.3f} < {baseline_f1 + min_gain:.3f}")   # код выхода 1
    print(f"OK: F1 {f1:.3f}")

X, y = make_classification(n_samples=1000, random_state=1)
X_tr, X_val, y_tr, y_val = train_test_split(X, y, random_state=1)

candidate = LogisticRegression().fit(X_tr, y_tr)
baseline = DummyClassifier(strategy="constant", constant=1).fit(X_tr, y_tr)
base_f1 = f1_score(y_val, baseline.predict(X_val))
print(round(base_f1, 3))                                  # 0.705
quality_gate(candidate, X_val, y_val, baseline_f1=base_f1)  # OK: F1 0.860
```

В реальном проекте вместо бейзлайна сравнивают с текущей продакшен-моделью из реестра, а результат пишут в `metrics.json`, чтобы видеть историю.

Smoke-тест для pytest может быть совсем коротким:

```python
def test_model_trains_and_predicts():
    X, y = make_classification(n_samples=50, random_state=0)
    model = LogisticRegression().fit(X, y)
    proba = model.predict_proba(X)[:, 1]
    assert proba.shape == (50,)
    assert ((proba >= 0) & (proba <= 1)).all()
```

## Подводные камни

- **Только тесты кода.** Код корректен, а модель хуже прежней — и её автоматически выкатили.
- **Полное обучение на каждый коммит.** Конвейер идёт часами, разработчики перестают ждать результата и обходят проверки.
- **Нестабильные тесты.** Без фиксированных seed метрика «прыгает», и quality gate срабатывает случайно; такие тесты быстро начинают игнорировать.
- **Сравнение на разных выборках.** Новая модель «лучше» только потому, что её оценили на более лёгких данных.
- **Секреты в конфигурации.** Ключи доступа к хранилищам должны храниться в секретах CI-системы, а не в репозитории.

## Итоги

- CI/CD для ML проверяет не только код, но и данные и модель; к нему добавляется continuous training.
- На каждый коммит — быстрые тесты: юнит-тесты признаков, схема данных, smoke-тест обучения.
- Полное обучение и оценка — при слиянии или по расписанию.
- Quality gate пропускает модель, только если она не хуже текущей на зафиксированной выборке.
- Воспроизводимость обеспечивают зафиксированные зависимости, seed, версии данных и описанный граф этапов.

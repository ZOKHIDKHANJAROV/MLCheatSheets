# Мультиагентные системы

<!-- время: 15 мин -->

> **О чём лекция.** Когда имеет смысл заменить одного LLM-агента командой, какие схемы организации бывают, сколько стоит их координация и почему «больше агентов» не значит «лучше».

## Зачем это нужно

Одному агенту с большим набором инструментов и длинной инструкцией трудно: контекст разрастается, модель путается в обязанностях, а независимые части задачи он выполняет по очереди. Естественная мысль — разделить работу: один агент ищет, другой пишет код, третий проверяет, четвёртый руководит. Так устроены человеческие команды.

Но у команды есть цена: агенты обмениваются сообщениями, а каждое сообщение — это токены, время и ещё одно место, где информация может исказиться. Поэтому главный вопрос лекции не «как собрать много агентов», а «когда это окупается и как посчитать расходы заранее».

## Интуиция: бригада на стройке

Представьте ремонт. Один мастер может сделать всё сам: он знает весь дом, ему не нужно ничего объяснять, но работает он последовательно. Бригада быстрее, потому что электрик и сантехник работают одновременно, и узкая специализация повышает качество. Но появляется прораб, который распределяет работу, и совещания, на которых тратится время. Если ремонт — одна розетка, бригада только мешает. Если ремонт — целый дом, без неё не обойтись.

- **Специализация** — узкая роль и короткий контекст у каждого агента.
- **Параллелизм** — независимые подзадачи выполняются одновременно.
- **Независимая проверка** — один агент проверяет работу другого.
- **Координация** — всё, что приходится передавать между агентами; это издержки.

## Как это работает

**Роли.** *Оркестратор* делит задачу и собирает результаты; *исполнители* решают узкие подзадачи со своими инструментами; *критик* (ревьюер) проверяет чужие результаты; *маршрутизатор* направляет запрос тому агенту, который подходит лучше.

**Паттерны организации.**

| паттерн | схема | где подходит |
|---|---|---|
| Supervisor | центр раздаёт задачи и собирает ответы | задача легко делится на независимые части |
| Pipeline | выход одного агента — вход следующего | последовательная обработка: черновик → правка → проверка |
| Debate | несколько агентов спорят, судья решает | спорные вопросы, проверка фактов |
| Swarm / handoff | агент передаёт управление другому по ходу диалога | маршрутизация по темам (приём → поддержка → оплата) |
| Иерархия | супервайзеры над группами исполнителей | очень большие задачи |

**Контекст: общий или изолированный.** Если у всех агентов общая история, согласованность выше, но токены растут у каждого и появляется шум. Если каждый получает только своё задание и нужные факты, дешевле и сфокусированнее, но то, что не передали явно, для агента не существует. На практике исполнителю дают короткое задание, а оркестратору возвращают сжатые итоги.

**Стоимость координации.** Подсчитаем сообщения за один раунд для n агентов:

- supervisor: оркестратор шлёт задачу каждому из k = n − 1 исполнителей и получает ответ: 2·(n − 1);
- pipeline: n − 1 передач по цепочке;
- «все-со-всеми»: каждый пишет каждому другому: n·(n − 1).

При n = 10 это 18, 9 и 90 сообщений. Каждое сообщение читает какая-то модель, то есть расходует входные токены. У supervisor есть узкое место: все ответы приходят оркестратору, и его контекст растёт быстрее остальных.

**Когда один агент лучше многих.** Задача короткая; шаги жёстко последовательны; нужен общий контекст целиком (например, правка одного файла); важны цена и задержка. Разумный путь — сначала сделать одного хорошего агента с инструментами, измерить качество, а команду добавлять только тогда, когда тесты показывают выигрыш.

## Пример на Python

Скрипт считает сообщения и токены для трёх схем и запускает маленький supervisor на заглушках вместо реальных моделей.

```python
def messages(n, scheme):
    """Сообщения за один раунд для n агентов (один из них — оркестратор)."""
    return {
        "supervisor": 2 * (n - 1),
        "pipeline": n - 1,
        "all_to_all": n * (n - 1),
    }[scheme]


def tokens(n, scheme, msg_tokens=300):
    return messages(n, scheme) * msg_tokens


for n in (3, 5, 10):
    row = {s: messages(n, s) for s in ("supervisor", "pipeline", "all_to_all")}
    print(n, row)
print("токенов за раунд при n = 10:", tokens(10, "all_to_all"))


def supervisor(task, workers):
    """Раздаёт подзадачи исполнителям и собирает результаты (вместо LLM — заглушки)."""
    subtasks = {name: f"{task}: часть для {name}" for name in workers}
    results = {}
    for name, sub in subtasks.items():
        run = workers[name]
        results[name] = run(sub)
    return " | ".join(f"{k} -> {v}" for k, v in results.items())


workers = {
    "поиск": lambda t: f"найдено по «{t}»",
    "анализ": lambda t: f"выводы по «{t}»",
}
print(supervisor("отчёт", workers))
```

Обратите внимание: при переходе от 5 к 10 агентам число сообщений у схемы «все-со-всеми» вырастает с 20 до 90, а у supervisor — с 8 до 18.

## Подводные камни

- **Агентов больше, чем нужно.** Команда из пяти агентов, решающая задачу на один вызов, дороже и медленнее и не лучше одного агента.
- **Нет лимита раундов и передач.** В схемах debate и handoff агенты могут бесконечно спорить или пересылать задачу по кругу. Задавайте максимум раундов и условие завершения.
- **Всем отдают всю историю.** Общий контекст раздувает токены и отвлекает исполнителей. Передавайте нужное, а не всё.
- **Размытые роли.** Если роли пересекаются, агенты дублируют работу или перекладывают её друг на друга.
- **Общие ошибки модели.** Агенты на одной модели нередко повторяют одни и те же заблуждения; дополнительные раунды debate их не исправят. Помогает разнообразие ролей, источников и внешняя проверка.
- **Нет измерений.** Без тестов, сравнивающих команду с одиночным агентом, неизвестно, окупается ли сложность.

## Итоги

- Мультиагентная система разделяет работу между ролями ради специализации, параллелизма и независимой проверки, но платит за это координацией.
- Основные паттерны: supervisor, pipeline, debate, handoff и иерархия.
- Число сообщений за раунд: supervisor — 2·(n − 1), pipeline — n − 1, «все-со-всеми» — n·(n − 1); каждое сообщение стоит токенов.
- Контекст лучше изолировать и передавать явно, а не раздавать всем целиком.
- Начинайте с одного агента; делите работу, когда измерения показывают выигрыш.

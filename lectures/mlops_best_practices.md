# MLOps Best Practices

<!-- время: 15 мин -->

> **О чём лекция.** Что такое MLOps и чем он отличается от DevOps: жизненный цикл ML-системы, трекинг экспериментов, реестр моделей, версии данных, безопасные выкатки и переобучение.

## Зачем это нужно

Одну модель можно обучить вручную в ноутбуке и вручную же положить на сервер. Проблемы начинаются, когда моделей несколько, их надо регулярно переобучать, а в команде больше одного человека. Через полгода уже никто не помнит, на каких данных обучена модель в продакшене, какие параметры дали лучший результат и почему вчерашнее переобучение ухудшило качество.

**MLOps** — набор практик и инструментов, которые делают жизненный цикл ML-моделей повторяемым, автоматическим и наблюдаемым. Это то же, что DevOps для обычного софта, но с поправкой на две вещи, которых в обычном софте нет: **данные** и **обученные модели**.

## Интуиция: в ML меняются три вещи, а не одна

В обычном приложении поведение определяется кодом. Поменяли код — поменялось поведение; не меняли — всё работает как раньше.

В ML поведение системы определяют три составляющие:

- **код** — предобработка, архитектура, обучение;
- **данные** — на чём обучали и что приходит сейчас;
- **модель** — конкретные веса, полученные из кода и данных.

Модель может испортиться, даже если код никто не трогал: просто изменились данные. Поэтому MLOps добавляет к DevOps версионирование данных, трекинг экспериментов, реестр моделей, мониторинг дрейфа и **continuous training** — автоматическое переобучение.

## Как это работает: жизненный цикл ML-системы

Типичный конвейер выглядит так:

1. Сбор данных.
2. Проверка и предобработка данных.
3. Построение признаков.
4. Обучение модели.
5. Оценка: метрики на отложенной выборке, сравнение с текущей моделью.
6. Развёртывание.
7. Мониторинг и, при необходимости, переобучение — и цикл начинается заново.

Зрелость MLOps часто описывают уровнями. На нулевом уровне всё делается руками в ноутбуках. На первом автоматизирован пайплайн обучения: его можно перезапустить одной командой или по расписанию. На втором автоматизированы и сборка, тестирование и выкатка самого пайплайна (CI/CD). Не каждой команде нужен второй уровень, но первый окупается почти всегда.

## Трекинг экспериментов

Каждый запуск обучения — эксперимент. Если не записывать параметры и результаты, через неделю вы не сможете повторить лучший результат. Инструменты вроде **MLflow** и **Weights & Biases** сохраняют для каждого запуска:

- параметры (learning rate, глубина деревьев, версия данных);
- метрики, в том числе по эпохам;
- артефакты: модель, графики, отчёты;
- версию кода (коммит Git) и окружение.

В MLflow это выглядит так:

```python
import mlflow

with mlflow.start_run():
    mlflow.log_param("max_depth", 4)
    mlflow.log_metric("cv_auc", 0.9855)
    mlflow.sklearn.log_model(model, "model")
```

Потом в интерфейсе можно отсортировать запуски по метрике, сравнить их и найти, при каких параметрах получен лучший результат.

## Реестр моделей и версии данных

**Model registry** — каталог обученных моделей с версиями и статусами: «кандидат», «staging», «production», «архив». У каждой версии есть ссылка на эксперимент, который её породил. Реестр отвечает на вопросы «какая модель сейчас в бою?» и «на какую версию откатиться?».

Данные слишком велики для Git, поэтому их версионируют отдельно. **DVC** хранит в Git маленький файл-указатель, а сами данные — в облачном хранилище:

```
dvc add data/dataset.csv
git add data/dataset.csv.dvc .gitignore
git commit -m "Датасет за октябрь"
dvc push
```

Теперь коммит в Git однозначно определяет и код, и данные, на которых обучена модель.

## Безопасные выкатки

Новую модель не стоит сразу отдавать всем пользователям. Обычная последовательность такая:

| этап | что происходит |
|---|---|
| shadow deployment | новая модель получает копию реального трафика и пишет предсказания в лог, но решения принимает старая |
| canary release | новая модель обслуживает небольшую долю трафика, например 5%; при проблемах её быстро выключают |
| A/B-тест | трафик делится на группы, и по бизнес-метрике со статистическим тестом решают, кто лучше |
| полная выкатка | победитель обслуживает всех и становится новым бейзлайном |

Shadow-режим ловит технические проблемы (ошибки, задержки, странные распределения прогнозов) без риска для пользователей. Canary ограничивает ущерб, если что-то всё же пошло не так.

## Когда переобучать модель

Есть три стратегии:

- **по расписанию** — раз в сутки, неделю или месяц. Просто и предсказуемо, но можно переобучать зря или опоздать;
- **по триггеру** — когда мониторинг видит дрейф данных или падение качества;
- **онлайн-обучение** — модель дообучается на потоке новых данных; применяется реже, потому что её сложнее контролировать.

Важно: переобученная модель не должна попадать в продакшен автоматически, если она хуже текущей. Перед выкаткой её сравнивают с моделью в бою на одной и той же свежей выборке — это и есть **quality gate**.

## Пример на Python

Минимальный трекинг экспериментов без внешних сервисов: каждый запуск — строка JSON в файле журнала. Идея та же, что в MLflow.

```python
import json, time
from pathlib import Path
from sklearn.datasets import make_classification
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import cross_val_score

X, y = make_classification(n_samples=2000, n_features=5, weights=[0.8], random_state=0)
log = Path("runs.jsonl")

for depth in [2, 4, 8]:
    clf = RandomForestClassifier(n_estimators=100, max_depth=depth, random_state=0)
    auc = cross_val_score(clf, X, y, cv=5, scoring="roc_auc").mean()
    run = {"time": time.strftime("%Y-%m-%d %H:%M"), "params": {"max_depth": depth},
           "metrics": {"cv_auc": round(auc, 4)}, "data": "make_classification(seed=0)"}
    with log.open("a", encoding="utf-8") as f:
        f.write(json.dumps(run, ensure_ascii=False) + "\n")

runs = [json.loads(line) for line in log.read_text(encoding="utf-8").splitlines()]
best = max(runs, key=lambda r: r["metrics"]["cv_auc"])
print(best["params"], best["metrics"])
```

В журнале записаны параметры, метрика и версия данных — по нему можно повторить любой запуск. Обратите внимание: лучшей может оказаться совсем не самая глубокая модель.

## Подводные камни

- **Инструменты раньше процессов.** Kubeflow и feature store без понятного пайплайна обучения только добавляют сложности. Начинайте с воспроизводимого скрипта обучения и трекинга экспериментов.
- **Нет версии данных.** Код в Git есть, а данных той версии уже нет — эксперимент невоспроизводим.
- **Автоматическое переобучение без проверки.** Свежая модель может оказаться хуже: например, если в новые данные попала ошибка разметки.
- **Мониторинг только инфраструктуры.** Сервис отвечает быстро и без ошибок, но предсказания давно неверные. Нужно следить и за данными, и за качеством.
- **Ручные шаги в пайплайне.** Любое «потом руками скопировать файл» рано или поздно забудут или сделают не так.

## Итоги

- MLOps — это DevOps плюс данные и модели: версионируются и проверяются все три составляющие.
- Трекинг экспериментов сохраняет параметры, метрики, артефакты и версию кода каждого запуска.
- Model registry хранит версии моделей и их статусы; DVC версионирует данные рядом с кодом.
- Выкатывайте осторожно: shadow → canary → A/B-тест → полная выкатка.
- Переобучайте по расписанию или по сигналу мониторинга, но выкатывайте только модель, прошедшую quality gate.

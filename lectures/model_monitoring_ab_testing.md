# Мониторинг моделей и A/B тестирование

<!-- время: 18 мин -->

> **О чём лекция.** Как понять, что модель в продакшене «сломалась», если она не выдаёт ни одной ошибки: что мониторить, как замерять дрейф (PSI, KS), что делать при метках с задержкой — и как честно проверить, что новая модель лучше старой, с помощью A/B-теста.

## Зачем это нужно

Обычный сервис ломается громко: падает, отвечает ошибкой 500, тормозит. ML-модель ломается тихо. Она продолжает быстро отвечать, но качество предсказаний постепенно падает: изменились клиенты, сезон, цены, поменяли формат данных в соседней системе. Без мониторинга об этом узнают через месяцы — по падающим бизнес-показателям.

Мониторинг и A/B-тесты отвечают на два разных вопроса:

- **мониторинг** — «не сломалась ли текущая модель?»;
- **A/B-тест** — «лучше ли новая модель старой для бизнеса?».

Вместе они замыкают цикл: мониторинг находит деградацию → модель переобучают → новую версию проверяют в A/B-тесте → победитель становится новым эталоном для мониторинга.

## Интуиция: приборная панель самолёта

Пилот не ждёт, пока самолёт начнёт падать: он смотрит на приборы — высоту, скорость, давление масла. Каждый прибор ловит свою беду, и часть из них предупреждает заранее.

У модели тоже несколько «приборов», и они срабатывают в разное время. Технические метрики видны сразу. Распределение входных данных — через часы. Истинное качество — только когда придут правильные ответы, а это может занять недели. Поэтому следить нужно за всеми слоями сразу.

## Как это работает: что мониторить

| слой | что смотрим | примеры сигналов |
|---|---|---|
| система | сервис инференса | задержка p50/p95/p99, запросы в секунду, ошибки 5xx, память |
| качество данных | вход модели | схема, доля пропусков, значения вне диапазона, новые категории |
| дрейф входа | распределение P(X) | PSI, KS-тест, χ² по признакам |
| предсказания | распределение P(ŷ) | средний скор, доля положительного класса, уверенность |
| качество | связь P(y∣X) | AUC, precision, MAE — когда пришли метки |
| бизнес | эффект | конверсия, выручка, жалобы, ручные исправления |

Основа всего — **лог предсказаний**: идентификатор запроса, время, версия модели, признаки и прогноз. Без него нельзя ни посчитать качество задним числом, когда придут метки, ни проанализировать A/B-тест.

## Как замерить дрейф

Сравнивают **референсное** распределение признака (обычно на обучающей выборке) и **текущее** (за последний день или неделю).

**PSI (Population Stability Index).** Признак разбивают на бины — обычно 10 квантилей референса — и сравнивают доли объектов в каждом бине:

```
PSI = Σ (aᵢ − eᵢ) · ln(aᵢ / eᵢ)
```

где eᵢ — доля в референсе, aᵢ — доля в текущем окне. Принятое правило: PSI < 0.1 — распределение стабильно, 0.1–0.25 — умеренный сдвиг, > 0.25 — значимый сдвиг.

**KS-тест** для непрерывных признаков: статистика D — максимальное расстояние между двумя эмпирическими функциями распределения. На больших выборках p-value почти всегда меньше 0.05 даже при ничтожной разнице, поэтому смотрят на величину D, а не только на p-value.

**χ²-тест** сравнивает частоты категорий для категориальных признаков.

Если признаков сотни, какие-то из них «сдвинутся» случайно. Помогают поправки на множественные проверки или алерты только по важным для модели признакам.

## Когда метки приходят с задержкой

В кредитном скоринге узнать, вернул ли клиент кредит, можно только через месяцы. Что делать до этого:

- следить за **прокси-сигналами**: дрейфом входа и распределением предсказаний. Если доля «одобренных» внезапно выросла вдвое, что-то произошло;
- использовать **ранние метки**: например, просрочку в первый месяц вместо дефолта за год;
- **размечать небольшую выборку вручную** — дорого, но быстро;
- когда метки придут, **досчитать качество** по логу предсказаний.

## Как устроен A/B-тест

1. **Гипотеза и метрика.** Например: «новая модель рекомендаций увеличит конверсию». Метрику и порог выбирают **до** старта.
2. **Размер выборки.** Его рассчитывают заранее по базовой конверсии, минимальному эффекту, который важно заметить (MDE), уровню значимости (обычно α = 0.05) и мощности (обычно 0.8).
3. **Разбиение.** Пользователей случайно и стабильно распределяют по группам, обычно хешем от идентификатора: A — старая модель, B — новая.
4. **Проведение.** Тест идёт ровно столько, сколько запланировано, — как правило, целыми неделями, чтобы учесть дни недели.
5. **Анализ.** Статистический тест (z-тест для долей, t-тест для средних, бутстреп) и проверка «защитных» метрик: задержка, жалобы, выручка.

Перед A/B-тестом стоит провести **A/A-тест** — две группы со старой моделью. Если он «находит» значимую разницу, сломано разбиение или подсчёт метрик.

## Почему нельзя подглядывать

Если смотреть на p-value каждый день и остановить тест, как только оно стало меньше 0.05, вероятность ложного «успеха» оказывается намного выше заявленных 5%. p-value случайно колеблется, и рано или поздно оно ненадолго опустится ниже порога даже при отсутствии эффекта. Это называется **peeking problem**. Решения: заранее фиксировать длительность теста или использовать методы последовательного тестирования, рассчитанные на многократные проверки.

## A/B-тест или бандиты

Многорукие бандиты (ε-greedy, Thompson sampling) постепенно отдают больше трафика варианту, который лучше работает. Они теряют меньше конверсий во время эксперимента, но хуже подходят для строгого вывода «B лучше A на столько-то процентов». A/B-тест — для решений и измерения эффекта, бандиты — для непрерывной оптимизации, например выбора баннера.

## Пример на Python

PSI и KS для признака со сдвигом, затем z-тест для конверсий двух групп:

```python
import numpy as np
from scipy import stats

def psi(ref, cur, bins=10, eps=1e-6):
    edges = np.quantile(ref, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(ref, edges)[0] / len(ref) + eps
    a = np.histogram(cur, edges)[0] / len(cur) + eps
    return float(np.sum((a - e) * np.log(a / e)))

rng = np.random.default_rng(0)
ref = rng.normal(0, 1, 10_000)        # обучающее окно
same = rng.normal(0, 1, 5_000)        # без изменений
shifted = rng.normal(0.5, 1, 5_000)   # среднее сдвинулось на 0.5σ
print(round(psi(ref, same), 3), round(psi(ref, shifted), 3))   # 0.002 0.235
print(round(stats.ks_2samp(ref, shifted).statistic, 3))         # 0.194

# A/B: конверсия 1000 из 20000 против 1090 из 20000
conv_a, n_a, conv_b, n_b = 1_000, 20_000, 1_090, 20_000
p_a, p_b = conv_a / n_a, conv_b / n_b
p = (conv_a + conv_b) / (n_a + n_b)
z = (p_b - p_a) / np.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
p_value = 2 * (1 - stats.norm.cdf(abs(z)))
print(f"{p_a:.2%} → {p_b:.2%}, z = {z:.2f}, p = {p_value:.3f}")   # 5.00% → 5.45%, z = 2.02, p = 0.043
```

Сдвиг на половину стандартного отклонения даёт PSI около 0.24 — на границе «значимого». Рост конверсии с 5% до 5.45% на 20 000 пользователях в группе статистически значим, но едва-едва: при меньшей выборке такой эффект можно было бы не заметить.

## Подводные камни

- **Мониторинг только инфраструктуры.** Сервис «зелёный», а прогнозы давно бесполезны.
- **Нет лога предсказаний.** Когда придут метки, качество посчитать будет не по чему.
- **Алерты на всё подряд.** Сотни признаков × ежедневные тесты = постоянный шум, и на алерты перестают реагировать.
- **Подглядывание в A/B-тесте** и остановка при первом значимом p-value.
- **Неслучайное или нестабильное разбиение.** Пользователь, который сегодня в A, а завтра в B, портит оба результата.
- **Слишком короткий тест.** Новизна (novelty effect) и дни недели искажают результат первых дней.

## Итоги

- ML-модели ломаются тихо, поэтому мониторят все слои: систему, данные, дрейф, предсказания, качество и бизнес.
- Дрейф измеряют PSI (порог 0.1 и 0.25), KS-тестом и χ²; при большой выборке смотрят на величину эффекта, а не только на p-value.
- При запаздывающих метках помогают прокси-сигналы, ранние метки и ручная разметка.
- A/B-тест: заранее выбранная метрика, рассчитанный размер выборки, стабильное случайное разбиение, фиксированная длительность.
- Нельзя останавливать тест при первом значимом результате.

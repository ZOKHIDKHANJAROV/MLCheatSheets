# Feature stores

<!-- время: 12 мин -->

> **О чём лекция.** Что такое feature store, зачем ему два хранилища — офлайн и онлайн, как point-in-time join защищает от утечки из будущего и когда такая система вам вообще не нужна.

## Зачем это нужно

Признаки (features) — самая трудоёмкая часть ML. «Сколько заказов сделал пользователь за 30 дней», «средний чек за неделю», «сколько раз карта использовалась за последний час» — каждый такой признак нужно посчитать, проверить и поддерживать.

В компании с несколькими моделями быстро появляются три проблемы:

- **дублирование**: разные команды считают «заказы за 30 дней» по-своему, с разными ошибками;
- **training-serving skew**: при обучении признак считали SQL-запросом по истории, а в онлайн-сервисе — другим кодом по свежим событиям, и значения не совпадают;
- **утечка из будущего**: при сборке обучающей выборки признак взяли по состоянию «на сегодня», хотя метка относилась к прошлому месяцу.

**Feature store** — централизованная система, которая хранит определения признаков, их значения и историю, и отдаёт одни и те же признаки и для обучения, и для инференса.

## Интуиция: склад с журналом изменений

Представьте склад, где у каждой полки есть журнал: что и когда на ней лежало. Для обучения модели нужно восстановить содержимое полок на прошлые даты — «что мы знали о клиенте 6 января?». Для онлайн-сервиса нужно мгновенно взять то, что лежит на полке сейчас.

Feature store — это склад с таким журналом: одно описание признака, два способа к нему обращаться.

## Как это работает

Основные компоненты:

| компонент | назначение |
|---|---|
| реестр признаков (registry) | описания: имя, тип, владелец, источник, способ расчёта, TTL |
| офлайн-хранилище | полная история значений для обучения; обычно хранилище данных или файлы Parquet |
| онлайн-хранилище | только последние значения с доступом за миллисекунды; обычно Redis, DynamoDB и т.п. |
| конвейеры расчёта | пакетные (по расписанию) и потоковые (из Kafka) задачи, которые пишут значения в оба хранилища |

Ключевые понятия:

- **entity (сущность)** — объект, к которому относится признак: пользователь, водитель, товар. Её идентификатор — ключ для поиска;
- **feature view** — группа признаков одной сущности из одного источника;
- **TTL** — сколько времени значение признака считается актуальным.

## Офлайн и онлайн

| | офлайн-хранилище | онлайн-хранилище |
|---|---|---|
| для чего | обучение и пакетный скоринг | онлайн-инференс |
| что хранит | всю историю значений с временными метками | только последнее значение для каждой сущности |
| объём запроса | миллионы строк | одна или несколько сущностей |
| требование к скорости | минуты допустимы | миллисекунды |

Обе части наполняются **одним и тем же кодом расчёта**. Это главное, что делает feature store средством против training-serving skew: признак невозможно посчитать для обучения одним способом, а для сервиса — другим.

## Point-in-time correct join

Чтобы собрать обучающую выборку, берут таблицу меток с временными метками («пользователь 1 ушёл 11 января») и присоединяют к ней признаки. Наивный join по последнему значению признака подставит то, что известно **сейчас** — в том числе события после 11 января. Модель обучится на информации из будущего и в бою будет работать хуже, чем на валидации.

**Point-in-time join** для каждой метки берёт последнее значение признака, известное **до момента метки**. В pandas это делает `merge_asof`, а в feature store — метод вроде `get_historical_features` в Feast:

```python
training_df = store.get_historical_features(
    entity_df=entity_df,                      # user_id + event_timestamp + метка
    features=["user_stats:orders_30d"],
).to_df()

online = store.get_online_features(
    features=["user_stats:orders_30d"],
    entity_rows=[{"user_id": 1}],
).to_dict()
```

## Пример на Python

Point-in-time join на pandas: для каждой метки — значение признака на момент метки, а не последнее известное.

```python
import pandas as pd

events = pd.DataFrame({          # история значений признака
    "user_id": [1, 1, 1, 2, 2],
    "ts": pd.to_datetime(["2026-01-01", "2026-01-05", "2026-01-10", "2026-01-02", "2026-01-08"]),
    "orders_30d": [1, 2, 3, 5, 6],
})
labels = pd.DataFrame({          # моменты, для которых известны метки
    "user_id": [1, 1, 2],
    "ts": pd.to_datetime(["2026-01-06", "2026-01-11", "2026-01-07"]),
    "churned": [0, 1, 0],
})

train = pd.merge_asof(labels.sort_values("ts"), events.sort_values("ts"),
                      on="ts", by="user_id", direction="backward")
print(train)
#    user_id         ts  churned  orders_30d
# 0        1 2026-01-06        0           2
# 1        2 2026-01-07        0           5
# 2        1 2026-01-11        1           3

online = events.sort_values("ts").groupby("user_id").last()["orders_30d"].to_dict()
print(online)   # {1: 3, 2: 6} — «онлайн-хранилище»: последние значения
```

Для метки пользователя 2 от 7 января взято значение 5, а не 6: значение 6 появилось только 8 января, и при обычном join по последнему значению в выборку попало бы будущее.

## Когда feature store не нужен

Feature store — серьёзная инфраструктура, и её поддержка стоит денег и времени. Скорее всего, он не нужен, если:

- модель одна или их несколько, но признаки не пересекаются;
- инференс только пакетный, и признаки считаются тем же SQL, что и для обучения;
- данных немного, и признаки дешевле пересчитать с нуля.

Он окупается, когда много моделей переиспользуют одни признаки, есть онлайн-инференс с жёсткими требованиями к задержке и потоковые признаки вроде «транзакций за последние 5 минут».

## Подводные камни

- **Обычный join вместо point-in-time.** Утечка из будущего, завышенная офлайн-метрика.
- **Неучтённая задержка данных.** Событие произошло в 10:00, но в хранилище попало только в 14:00. Для честной выборки нужна метка времени появления данных, а не только время события.
- **Устаревшие онлайн-значения.** Потоковый конвейер упал, и онлайн-хранилище отдаёт признаки вчерашнего дня. Нужны TTL и мониторинг свежести.
- **Feature store ради одной модели.** Инфраструктура сложнее самой задачи.
- **Нет владельцев признаков.** Через год в реестре сотни признаков, и никто не знает, какие из них ещё правильные.

## Итоги

- Feature store хранит определения и значения признаков и отдаёт их одинаково для обучения и инференса.
- Офлайн-хранилище — полная история для обучения, онлайн — последние значения за миллисекунды; наполняются одним кодом.
- Это главное средство против training-serving skew и дублирования признаков между командами.
- Point-in-time join берёт значение признака на момент метки и защищает от утечки из будущего.
- Для одной модели с пакетным инференсом feature store обычно избыточен.

# Prompt Engineering для LLM

<!-- время: 15 мин -->

> **О чём лекция.** Как формулировать запросы к большим языковым моделям, чтобы получать точные и предсказуемые ответы: структура хорошего промпта, примеры (few-shot), рассуждение по шагам, структурированный вывод, проверка ответов — и почему промпт никогда не заменяет оценку качества и защиту от prompt injection.

## Зачем это нужно

Большая языковая модель (LLM) умеет решать огромное число задач без дообучения: классифицировать отзывы, извлекать данные из документов, писать код, переводить, суммировать. Но качество ответа сильно зависит от того, **как** сформулирована задача. Один и тот же запрос, сформулированный размыто и точно, может дать ответ на 50% и на 95% правильный.

**Prompt engineering** — практика составления запросов (промптов) так, чтобы модель надёжно делала то, что нужно. Для ML-инженера это часто самый быстрый способ получить работающий прототип: вместо сбора разметки и обучения классификатора — хорошо продуманный промпт и набор тестов.

## Интуиция: инструкция для умного стажёра

Представьте, что вы даёте задание очень эрудированному, но совершенно новому стажёру. Он не знает ваш проект, ваших клиентов, формат отчётов и того, что для вас «хорошо». Если сказать «разберись с отзывами», он что-то сделает, но вряд ли то, что вы ожидали.

Хорошее задание стажёру содержит:

- **контекст**: кто мы, для чего это нужно;
- **задачу**: что конкретно сделать;
- **ограничения**: чего делать не надо, какой длины ответ;
- **формат результата**: таблица, JSON, три пункта;
- **примеры**: «вот так выглядит хороший ответ».

С LLM всё так же. Модель не читает ваших мыслей — всё, что важно, должно быть в тексте запроса.

## Как это работает: структура промпта

Типичный запрос к модели через API состоит из сообщений с ролями:

- **system** — постоянные правила и роль: «Ты помощник службы поддержки интернет-магазина. Отвечай кратко и вежливо»;
- **user** — конкретный запрос пользователя;
- **assistant** — ответы модели (в истории диалога или как образец).

Хороший промпт обычно включает несколько блоков, чётко отделённых друг от друга:

```
Роль и контекст:   Ты анализируешь отзывы покупателей электроники.
Задача:            Определи тональность отзыва.
Ограничения:       Если отзыв не о товаре, ответь "neutral".
Формат:            Только JSON: {"sentiment": "positive" | "negative" | "neutral"}
Примеры:           ...
Данные:            <<<текст отзыва>>>
```

Разделители (`<<< >>>`, теги, заголовки) помогают модели отличать инструкции от данных.

## Основные приёмы

**Zero-shot и few-shot.** Zero-shot — только инструкция. Few-shot — инструкция плюс несколько примеров «вход → правильный выход». Примеры особенно помогают, когда важен формат или есть тонкие правила разметки. Берите разнообразные примеры, включая пограничные случаи, и следите, чтобы классы были представлены сбалансированно — модель склонна копировать распределение и порядок примеров.

**Chain-of-thought (рассуждение по шагам).** Для задач с несколькими шагами (арифметика, логика, анализ) модель отвечает точнее, если сначала распишет рассуждение, а затем даст ответ. Это можно попросить явно: «Сначала рассуждай по шагам, затем дай итоговый ответ в последней строке». Многие современные модели рассуждают и сами, но явная просьба всё равно полезна для сложных задач. Для простых задач (классификация коротких текстов) рассуждение лишь удлиняет и удорожает ответ.

**Структурированный вывод.** Если ответ будет читать программа, попросите строгий формат (JSON по схеме) и **проверяйте** его кодом. Многие API умеют принудительно выдавать JSON по заданной схеме — используйте это, когда доступно.

**Self-consistency.** Задать один вопрос несколько раз с ненулевой температурой и выбрать самый частый ответ. Повышает точность в задачах рассуждения ценой нескольких запросов.

**Разбиение задачи.** Сложную задачу надёжнее решить цепочкой простых запросов: сначала извлечь факты, затем проанализировать, затем написать итог. Каждый шаг проще проверить и отладить.

**Предоставление знаний (RAG).** Модель не знает ваших внутренних документов и может ошибаться в фактах. Retrieval-Augmented Generation — найти релевантные фрагменты в базе знаний и вставить их в промпт с инструкцией «отвечай только по приведённым документам; если ответа нет — скажи об этом».

**ReAct и инструменты.** Модель может чередовать рассуждения и действия: вызвать поиск, калькулятор или функцию вашего кода, получить результат и продолжить. На этом построены агенты.

## Температура и воспроизводимость

Параметр `temperature` управляет случайностью ответа. Для извлечения данных, классификации и кода ставьте низкую температуру (0–0.3) — ответы стабильнее. Для генерации идей и творческих текстов — выше. Даже при нулевой температуре ответы не всегда идеально воспроизводимы, поэтому системы на LLM оценивают на наборах примеров, а не по одному запуску.

## Prompt engineering как инженерия

Промпт — это код, и с ним обращаются как с кодом:

1. Соберите **набор тестовых примеров** с правильными ответами (хотя бы 30–100), включая сложные случаи.
2. Посчитайте метрику (accuracy, F1, доля корректного JSON).
3. Меняйте промпт и сравнивайте метрику, а не впечатление от пары удачных ответов.
4. Храните промпты в системе контроля версий и проверяйте заново при смене модели — другая модель или версия может вести себя иначе.

## Пример на Python

Few-shot промпт для классификации отзывов, проверка формата ответа и голосование для self-consistency. Сама модель здесь не вызывается — показана логика вокруг неё:

```python
import json
from collections import Counter

def build_prompt(review):
    examples = [
        ("Доставили быстро, всё работает.", "positive"),
        ("Сломалось через два дня.", "negative"),
        ("Нормально, но упаковка мятая.", "neutral"),
    ]
    shots = "\n\n".join(f"Отзыв: {t}\nОтвет: {json.dumps({'sentiment': s})}" for t, s in examples)
    return (
        "Ты классифицируешь отзывы покупателей.\n"
        'Ответь только JSON вида {"sentiment": "positive" | "negative" | "neutral"}.\n\n'
        f"{shots}\n\n"
        f"Отзыв: <<<{review}>>>\nОтвет:"      # пользовательский текст отделён разделителями
    )

def parse_answer(text):
    """Модель может ошибиться в формате — проверяем, а не верим на слово."""
    try:
        label = json.loads(text)["sentiment"]
    except (json.JSONDecodeError, KeyError, TypeError):
        return None
    return label if label in {"positive", "negative", "neutral"} else None

print(build_prompt("Отличный чайник!")[-30:])
print(parse_answer('{"sentiment": "positive"}'))     # positive
print(parse_answer("Думаю, отзыв положительный"))   # None — нужен повторный запрос

# Self-consistency: несколько ответов с temperature > 0 и голосование
answers = ["11", "11", "12", "11", "9"]               # ответы модели на одну задачу
print(Counter(answers).most_common(1)[0][0])         # 11
```

В реальном коде `build_prompt(...)` отправляется в API выбранной модели, а ответ проходит через `parse_answer`; если формат неверный — запрос повторяют или помечают пример для ручной проверки.

## Подводные камни

- **Prompt injection.** Если в промпт попадает недоверенный текст (письмо, веб-страница, отзыв), он может содержать инструкции вроде «игнорируй предыдущие указания и …». Модель может им последовать. Разделители и формулировки снижают риск, но не устраняют его. Не давайте модели, читающей недоверенные данные, права на опасные действия без проверки, и не кладите в промпт секреты.
- **Галлюцинации.** Модель уверенно сочиняет факты, ссылки и цифры. Требуйте опоры на приведённые документы и разрешайте ответ «не знаю».
- **Оценка «на глаз».** Пара удачных ответов ничего не доказывает. Нужен тестовый набор и метрика.
- **Слишком длинный промпт.** Важные инструкции теряются среди лишнего текста. Убирайте ненужное, самое важное формулируйте явно.
- **Противоречивые инструкции.** «Будь кратким» и «объясни подробно» в одном промпте дают непредсказуемый результат.
- **Зависимость от модели.** Промпт, отлаженный под одну модель, может работать хуже на другой. Перепроверяйте при смене модели.
- **Персональные данные.** Учитывайте, какие данные вы отправляете во внешний API и какие правила к ним применимы.

## Итоги

- Качество ответа LLM сильно зависит от формулировки: контекст, задача, ограничения, формат, примеры.
- Few-shot примеры задают формат и правила; chain-of-thought помогает в многошаговых задачах.
- Для программной обработки — строгий структурированный вывод и проверка кодом.
- RAG даёт модели нужные знания, разбиение задачи и инструменты повышают надёжность.
- Промпт — это код: тестовый набор, метрика, версии; помните о prompt injection и галлюцинациях.

# Оценка ИИ-агентов

<!-- время: 15 мин -->

> **О чём лекция.** Как измерять качество агента, который каждый раз действует чуть иначе: от доли решённых задач и метрик pass@k и pass^k до LLM-судьи, бенчмарков, регрессионных наборов и трасс.

## Зачем это нужно

Агент — это LLM, которая в цикле вызывает инструменты и принимает решения. Его поведение случайно и зависит от длинной цепочки шагов: одна и та же задача сегодня решается, завтра нет. Поэтому фраза «я попробовал, работает» ничего не доказывает. Нужны фиксированный набор задач, повторные попытки и метрики, которые отвечают на вопросы: решает ли агент задачу вообще, делает ли это стабильно и сколько это стоит.

Без оценки нельзя понять, стала ли новая версия промпта или модели лучше, и невозможно вовремя заметить регрессию.

## Интуиция: экзамен с пересдачами

Представьте студента, которому дают одну и ту же задачу несколько раз. Две разные оценки:

- «Хоть раз решил из k попыток» — показывает, на что студент способен. Это **pass@k**.
- «Решил все k попыток подряд» — показывает, можно ли на него положиться. Это **pass^k**.

Для генератора кода с автотестами хватит первого: можно сгенерировать k вариантов и выбрать тот, что прошёл тесты. Для агента поддержки клиентов, где каждый сбой — реальная проблема, важно второе.

## Как это работает

### Успешность задачи

Каждая задача содержит начальное состояние, цель и **способ проверки**. Лучше всего проверять итоговое состояние среды (тесты прошли, запись в базе создана), а не красоту текста ответа. Доля успеха: success_rate = (1/N) · Σ success_i. При малом числе задач нужен доверительный интервал, иначе разница в пару процентных пунктов — шум.

### pass@k и pass^k

Пусть на задаче сделано n попыток, из них c успешных. Несмещённые оценки:

```
pass@k = 1 − C(n − c, k) / C(n, k)
pass^k = C(c, k) / C(n, k)
```

Если истинная доля успеха p, то pass@k → 1 − (1 − p)ᵏ растёт с k, а pass^k → pᵏ падает. При p = 0,8 и k = 4 получаем pass@4 ≈ 0,998, но pass^4 ≈ 0,41. Метрики считают по каждой задаче отдельно, затем усредняют по набору. Метрика pass^k известна по бенчмарку τ-bench.

### Метрики траектории

Помимо результата записывают путь: число шагов, токены и стоимость, латентность (медиана и p95), долю ошибок инструментов. Агент, который решает ту же долю задач вдвое дороже или вдвое медленнее, — не лучший. Рост числа шагов часто сигнализирует о зацикливании.

### LLM-as-a-judge

Если точной проверки нет (качество объяснения, вежливость), ответ или трассу оценивает другая LLM по рубрике. У судьи есть смещения: позиционное (предпочитает вариант на определённом месте), к многословности, самопредпочтение (своя модель оценивается выше). Меры: менять порядок вариантов и учитывать только устойчивые вердикты, давать чёткую рубрику, брать судью другой модели и **калибровать его на примерах, размеченных людьми**.

### Бенчмарки

- **SWE-bench** — исправление реальных issue из репозиториев GitHub, успех определяется тестами.
- **GAIA** — вопросы для универсального ассистента, требующие поиска, работы с файлами и рассуждений.
- **WebArena** — задачи в самодостаточных веб-средах, проверка по итоговому состоянию.
- **τ-bench** — диалог агента с имитируемым пользователем по правилам домена, сравнивается состояние базы, вводится pass^k.

Общие принципы хороших бенчмарков: проверяемый результат, воспроизводимая среда, защита от утечки тестов в обучающие данные. Публичный бенчмарк не заменяет собственный набор под вашу задачу.

### Регрессионные наборы и трассы

Каждый сбой из реальной эксплуатации превращают в тестовую задачу. Набор версионируют вместе с промптами, моделью и инструментами и запускают при каждом изменении. Для разбора ошибок логируют **трассы**: сообщения, вызовы инструментов, аргументы, ответы, время и токены (без секретов и персональных данных).

## Пример на Python

Оценщики pass@k и pass^k по таблице попыток (без обращения к реальной модели):

```python
from math import comb


def pass_at_k(n: int, c: int, k: int) -> float:
    """Несмещённая оценка: хотя бы одна из k попыток успешна."""
    if n - c < k:
        return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)


def pass_hat_k(n: int, c: int, k: int) -> float:
    """Оценка pass^k: все k попыток успешны."""
    return comb(c, k) / comb(n, k)


# (задача, число попыток n, число успехов c)
tasks = [("refund", 10, 9), ("cancel", 10, 6), ("address", 10, 10), ("complex", 10, 2)]

for k in (1, 4):
    at = sum(pass_at_k(n, c, k) for _, n, c in tasks) / len(tasks)
    hat = sum(pass_hat_k(n, c, k) for _, n, c in tasks) / len(tasks)
    print(f"k={k}: pass@k={at:.3f}  pass^k={hat:.3f}")

# Теоретическое сравнение при доле успеха p = 0.8
p = 0.8
print(round(1 - (1 - p) ** 4, 4), round(p ** 4, 4))
```

Видно, что при росте k средний pass@k растёт, а pass^k падает. Если оценить надёжность только по pass@k, получится завышенная картина.

## Подводные камни

- **Одна попытка на задачу.** Результат случаен; делайте повторы и считайте доверительные интервалы.
- **Усреднение по попыткам вместо задач.** Задачи с разным числом попыток вносят разный вклад; считайте метрику по задаче, потом усредняйте.
- **Непроверенный судья.** Судья-LLM без калибровки по людям может систематически завышать длинные ответы. Выборочно сверяйте его с ручной оценкой.
- **Проверка текста вместо состояния.** Агент может написать «готово», ничего не сделав. Проверяйте итог в среде.
- **Утечка и переобучение под набор.** Если подбирать промпт по тестовым задачам, итоговая цифра завышена; держите отложенный набор.
- **Сравнение без учёта стоимости.** Сопоставляйте успех при заданном бюджете и латентности.

## Итоги

- Агент недетерминирован: оценка требует набора задач, повторов и метрик по задачам.
- pass@k = 1 − C(n−c, k)/C(n, k) — способность решить; pass^k = C(c, k)/C(n, k) — надёжность.
- Кроме успеха измеряют шаги, стоимость и латентность, логируют трассы.
- LLM-судья смещён: меняйте порядок вариантов, калибруйте на людях.
- Регрессионный набор строится из реальных сбоев и запускается при каждом изменении.

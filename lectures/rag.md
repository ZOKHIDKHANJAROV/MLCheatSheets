# RAG: генерация с поиском

<!-- время: 20 мин -->

> **О чём лекция.** Как заставить языковую модель отвечать по вашим документам, а не по памяти: из каких шагов состоит RAG, как резать текст на чанки, зачем объединять поиск по словам и по смыслу, чем измерять качество поиска и где такие системы ломаются.

## Зачем это нужно

Языковая модель знает только то, что попало в обучающие данные до определённой даты, и не видит ваших внутренних документов: регламентов, договоров, базы знаний. Если спросить её о них, она может ответить уверенно и неверно — выдумать правдоподобную деталь.

Дообучать модель на каждом изменении документов дорого и медленно. Проще сделать иначе: перед ответом **найти** нужные фрагменты и показать их модели прямо в запросе. Эта схема называется **RAG** — Retrieval-Augmented Generation, «генерация, дополненная поиском». Знания обновляются заменой записей в индексе, ответ можно подкрепить ссылками, а модель опирается на текст перед глазами.

## Интуиция: экзамен с открытой книгой

Представьте экзамен, на котором разрешено пользоваться учебником. Хороший студент не пересказывает учебник целиком и не зубрит его: он быстро находит нужные страницы, прочитывает их и отвечает по ним.

- **Учебник** — база документов.
- **Оглавление и предметный указатель** — индекс для поиска.
- **Найденные страницы** — контекст, который кладётся в prompt.
- **Ответ студента** — генерация.

Если студент нашёл не ту страницу, ответ будет плохим, как бы он ни писал. Так и в RAG: **качество ответа ограничено качеством поиска**.

## Как это работает

### Пайплайн

Индексация выполняется заранее (офлайн):

1. Загрузить и очистить документы.
2. Нарезать на **чанки** — фрагменты, которые будут единицей поиска.
3. Превратить каждый чанк в вектор-эмбеддинг.
4. Сохранить вектор, текст и метаданные (источник, дата, раздел) в индекс.

Запрос обрабатывается онлайн:

1. Превратить вопрос в вектор и найти top-k ближайших чанков.
2. При необходимости объединить с поиском по словам и **переранжировать** кандидатов.
3. Собрать контекст из лучших чанков в пределах бюджета токенов.
4. Попросить модель ответить **только по контексту**, со ссылками на источники.

### Чанкинг

Чанк слишком крупный — в нём много постороннего, он «размывает» смысл вектора и расходует окно. Чанк слишком мелкий — теряется окружение, ответ может оказаться «через соседний абзац». Ориентиры: несколько сотен токенов на чанк и перекрытие (**overlap**) 10–20% размера; точные значения подбирают по метрикам поиска на своих данных.

Окно размера `size` сдвигается с шагом `size − overlap`, поэтому для текста из n токенов получается примерно ⌈(n − overlap) / (size − overlap)⌉ чанков. Перекрытие повторяет границу соседних чанков: мысль, оказавшаяся на стыке, целиком попадёт хотя бы в один из них. Если есть структура (заголовки, абзацы), резать лучше по ней, а не посреди предложения.

### Гибридный поиск

Поиск по эмбеддингам понимает перефразировки («вернуть деньги» ≈ «возврат средств»), но легко промахивается на редких словах: артикулах, кодах ошибок, фамилиях. Лексический поиск **BM25** ищет по точным словам запроса:

```
score(q, d) = Σₜ IDF(t) · f(t, d) · (k₁ + 1) / ( f(t, d) + k₁ · (1 − b + b · len(d) / avgdl) )
```

Здесь f(t, d) — сколько раз терм t встретился в документе d, len(d) — длина документа, avgdl — средняя длина, IDF(t) — «редкость» терма (редкие слова весомее), k₁ ≈ 1.2–2 и b ≈ 0.75 — параметры насыщения и учёта длины.

Два списка результатов объединяют без подбора весов с помощью **RRF** (Reciprocal Rank Fusion): каждый документ получает Σ 1 / (k + rank), где rank — его место в каждом из списков, а k обычно около 60. Документы, высоко стоящие в обоих списках, выигрывают.

### Реранкинг

Быстрый поиск по заранее посчитанным векторам даёт 20–100 кандидатов. Затем более точная и медленная модель (**cross-encoder**) смотрит на пару «вопрос + чанк» целиком и пересортировывает кандидатов; в prompt идут 3–5 лучших. Реранкер повышает точность верхушки списка, но не может вернуть чанк, которого нет среди кандидатов.

### Сборка контекста

Чанки добавляют по убыванию релевантности, пока хватает бюджета токенов; каждый подписывают источником. Исследования показывают, что модели хуже используют информацию из середины длинного контекста («lost in the middle»), поэтому самые важные чанки ставят в начало и конец, а k не раздувают.

### Метрики поиска

Поиск оценивают отдельно от генерации: на наборе вопросов с известными релевантными чанками (документами).

| метрика | формула | что показывает |
|---|---|---|
| recall@k | (релевантные в top-k) / (все релевантные) | попал ли нужный чанк в контекст |
| precision@k | (релевантные в top-k) / k | сколько в контексте мусора |
| MRR | среднее по запросам от 1 / rank первого релевантного | насколько высоко стоит первый верный результат |

Если у запроса нет релевантного результата в списке, его вклад в MRR равен нулю.

## Пример на Python

Мини-RAG без внешних сервисов: «игрушечный» эмбеддинг (хэшированный мешок слов), BM25, слияние RRF и метрики поиска на пяти вопросах. Ответ модели не генерируем — оцениваем именно поиск.

```python
import re
import zlib
import numpy as np

docs = {
    "return": "Возврат товара возможен в течение 14 дней с момента покупки. "
              "Для возврата нужен чек. Деньги возвращаются на карту за 5 рабочих дней.",
    "delivery": "Доставка по городу занимает 3 дня. Самовывоз из магазина бесплатный "
                "и доступен на следующий день после заказа.",
    "warranty": "Гарантия на технику действует 24 месяца. Гарантийный ремонт "
                "выполняется в сервисном центре бесплатно.",
}


def tokens(text):
    return re.findall(r"\w+", text.lower())


def chunk(text, size=12, overlap=4):
    words = text.split()
    step = size - overlap
    return [" ".join(words[i:i + size]) for i in range(0, max(len(words) - overlap, 1), step)]


chunks, owner = [], []
for name, text in docs.items():
    for c in chunk(text):
        chunks.append(c)
        owner.append(name)


def embed(text, dim=128):
    v = np.zeros(dim)
    for w in tokens(text):
        v[zlib.crc32(w.encode()) % dim] += 1.0
    n = np.linalg.norm(v)
    return v / n if n else v


E = np.stack([embed(c) for c in chunks])


def dense_rank(q):
    return list(np.argsort(-(E @ embed(q))))


def bm25_rank(q, k1=1.5, b=0.75):
    toks = [tokens(c) for c in chunks]
    avgdl = np.mean([len(t) for t in toks])
    scores = np.zeros(len(chunks))
    for term in set(tokens(q)):
        n = sum(term in t for t in toks)
        idf = np.log(1 + (len(chunks) - n + 0.5) / (n + 0.5))
        for i, t in enumerate(toks):
            f = t.count(term)
            scores[i] += idf * f * (k1 + 1) / (f + k1 * (1 - b + b * len(t) / avgdl))
    return list(np.argsort(-scores))


def rrf(rankings, k=60):
    score = {}
    for ranking in rankings:
        for rank, i in enumerate(ranking, 1):
            score[i] = score.get(i, 0.0) + 1 / (k + rank)
    return sorted(score, key=score.get, reverse=True)


def doc_order(ranked):
    """Порядок документов по первому появлению их чанков в ранжировании."""
    seen = []
    for i in ranked:
        if owner[i] not in seen:
            seen.append(owner[i])
    return seen


gold = {
    "сколько дней на возврат товара": "return",
    "когда доставят заказ по городу": "delivery",
    "срок гарантии на технику": "warranty",
    "бесплатный самовывоз": "delivery",
    "сколько ждать посылку": "delivery",   # общих слов с текстом нет
}

for name, search in [("dense", dense_rank), ("bm25", bm25_rank),
                     ("hybrid", lambda q: rrf([dense_rank(q), bm25_rank(q)]))]:
    ranks = [doc_order(search(q)).index(d) + 1 for q, d in gold.items()]
    recall1 = np.mean([r <= 1 for r in ranks])
    mrr = np.mean([1 / r for r in ranks])
    print(f"{name:7s} recall@1 = {recall1:.2f}  MRR = {mrr:.2f}")
```

Метрики считаются для каждого способа поиска на одних и тех же вопросах — так и сравнивают варианты на практике. Значения зависят от игрушечных данных: игрушечный эмбеддинг ловит только совпадения слов, а настоящая модель дала бы смысловую близость. Вопрос «сколько ждать посылку» не делит со словами текста ни одного слова — оба метода на нём промахиваются, и это стоит 0.2 по recall@1. Именно такие перефразировки умеют ловить настоящие эмбеддинги. Попробуйте менять `size` и `overlap` и смотрите, как меняются метрики.

## Подводные камни

- **Нужного фрагмента нет в контексте.** Чанк разрезан неудачно или k слишком мал. Симптом — низкий recall@k. Лечат перекрытием, чанками по структуре, увеличением k вместе с реранкингом.
- **«Lost in the middle».** Нужный чанк в контексте есть, но модель его не использует. Помогают меньше чанков, порядок «важное по краям», реранкинг.
- **Устаревшие данные.** Индекс не обновили, в нём лежат старые версии документов. Нужны даты и версии в метаданных, переиндексация по расписанию и удаление устаревших записей.
- **Плотный поиск не находит коды и имена.** Добавьте BM25, то есть гибридный поиск.
- **Модель отвечает «по мотивам».** В prompt нет требования опираться только на контекст и признавать, что ответа нет.
- **Оценка «на глаз».** Качество поиска нужно мерить отдельно (recall@k, MRR) на наборе вопросов, иначе непонятно, что чинить — поиск или генерацию.
- **Эмбеддинги разных моделей.** Запрос и документы должны кодироваться одной и той же моделью.

## Итоги

- RAG = поиск + контекст + генерация: модель отвечает по найденным фрагментам, а не по памяти.
- Индексация идёт офлайн (чанки → эмбеддинги → индекс), запрос — онлайн (поиск → реранкинг → сборка контекста → ответ).
- Размер чанка и overlap подбирают по метрикам; шаг окна равен size − overlap.
- Гибридный поиск (BM25 + эмбеддинги, слияние RRF) закрывает слабые стороны каждого метода; реранкер уточняет верх списка.
- Поиск оценивают отдельно: recall@k, precision@k, MRR.
- Типичные сбои: потерянный контекст, «lost in the middle», устаревшие данные.

# Вызов инструментов (function calling)

<!-- время: 15 мин -->

> **О чём лекция.** Как языковая модель «вызывает функции»: что такое JSON-схема инструмента, как устроен цикл tool_call → выполнение → tool_result, зачем проверять аргументы и ограничивать число шагов.

## Зачем это нужно

Языковая модель умеет только генерировать текст. Она не знает сегодняшней погоды, не умеет точно перемножать большие числа и не может отправить письмо. Но если дать ей способ **попросить** внешнюю функцию выполнить работу и получить результат, она превращается из «рассказчика» в исполнителя. Этот механизм называется **вызовом инструментов** (tool use, function calling) и лежит в основе почти любого агента.

## Интуиция: официант и кухня

Модель — официант, который принимает заказ и общается с гостем, а функции — кухня. Официант сам не готовит. Он записывает на бланке заказа: **что именно** приготовить и **с какими параметрами** («стейк, средней прожарки»), и передаёт бланк на кухню. Кухня выполняет заказ, возвращает блюдо, а официант объясняет результат гостю. Если на кухне сказали «такого нет», официант пересматривает заказ.

Важно: бланк заполняет модель, но **готовит и отвечает за безопасность ваше приложение**. Модель лишь предлагает вызов.

## Как это работает

### JSON-схема инструмента

Каждому инструменту даётся описание в формате JSON-схемы: имя, назначение и параметры.

```
{
  "name": "get_weather",
  "description": "Температура воздуха в городе",
  "parameters": {
    "type": "object",
    "properties": {
      "city":  {"type": "string"},
      "units": {"type": "string", "enum": ["c", "f"]}
    },
    "required": ["city"]
  }
}
```

Модель выбирает инструмент и заполняет аргументы, опираясь на `name`, `description` и схему параметров. Поэтому описание — это инструкция: что делает функция и когда её применять. Точные названия полей запроса и ответа зависят от поставщика модели, но идея везде одна.

### Цикл вызова

1. Приложение отправляет модели сообщения и список схем инструментов.
2. Модель отвечает либо текстом, либо запросом `tool_call`: идентификатор, имя функции, аргументы.
3. Приложение **проверяет** аргументы и выполняет функцию.
4. Результат добавляется в историю как `tool_result` с тем же идентификатором.
5. Модель вызывается снова. Цикл продолжается, пока она не ответит текстом или не исчерпается лимит шагов.

### Параллельные вызовы

За один ход модель может вернуть несколько `tool_call` — например, запросить погоду сразу в двух городах. Независимые вызовы можно выполнять одновременно, но каждый результат нужно вернуть с идентификатором своего вызова. Если результат первого вызова нужен для второго, они идут последовательно, в разных ходах.

### Валидация и ошибки

Модель может пропустить обязательное поле, перепутать тип или выдумать аргумент либо функцию. Поэтому:

- проверяйте имя функции по реестру и аргументы по схеме до выполнения;
- ошибку (валидации или самого инструмента) возвращайте модели как `tool_result` с понятным текстом — она сможет исправить вызов;
- не позволяйте исключению инструмента ронять весь цикл.

### Ограничения

Ограничивайте число шагов (`max_steps`), стоимость, время работы инструмента; разрешайте только нужные функции; необратимые действия подтверждайте у человека.

## Пример на Python

Вместо реальной модели — заглушка, которая сначала запрашивает два параллельных вызова (один с неверным значением `units`), а после ошибки исправляет вызов.

```python
SCHEMA = {
    "name": "get_weather",
    "description": "Температура воздуха в городе",
    "parameters": {
        "type": "object",
        "properties": {
            "city": {"type": "string"},
            "units": {"type": "string", "enum": ["c", "f"]},
        },
        "required": ["city"],
    },
}
TYPES = {"string": str, "integer": int, "number": (int, float)}

def validate(args, schema):
    """Возвращает список ошибок (пустой — аргументы корректны)."""
    params = schema["parameters"]
    errors = [f"нет поля {k}" for k in params.get("required", []) if k not in args]
    for key, value in args.items():
        spec = params["properties"].get(key)
        if spec is None:
            errors.append(f"лишнее поле {key}")
        elif not isinstance(value, TYPES[spec["type"]]):
            errors.append(f"{key}: ожидался {spec['type']}")
        elif "enum" in spec and value not in spec["enum"]:
            errors.append(f"{key}: допустимо {spec['enum']}")
    return errors

WEATHER = {"Москва": 5, "Казань": 3}            # условные данные

def get_weather(city, units="c"):
    t = WEATHER[city]
    return t if units == "c" else round(t * 9 / 5 + 32, 1)

REGISTRY = {"get_weather": (SCHEMA, get_weather)}

def execute(call):
    """Выполняет вызов и всегда возвращает tool_result (даже при ошибке)."""
    result = {"role": "tool", "tool_call_id": call["id"], "is_error": False}
    schema, fn = REGISTRY.get(call["name"], (None, None))
    if fn is None:
        return {**result, "is_error": True, "content": "неизвестный инструмент"}
    errors = validate(call["arguments"], schema)
    if errors:
        return {**result, "is_error": True, "content": "; ".join(errors)}
    try:
        return {**result, "content": fn(**call["arguments"])}
    except Exception as exc:                      # ошибка инструмента — тоже наблюдение
        return {**result, "is_error": True, "content": f"сбой: {exc!r}"}

def fake_llm(messages):
    """Заглушка модели: сначала два параллельных вызова (один с ошибкой)."""
    tools = [m for m in messages if m["role"] == "tool"]
    if not tools:
        return {"tool_calls": [
            {"id": "c1", "name": "get_weather", "arguments": {"city": "Москва"}},
            {"id": "c2", "name": "get_weather", "arguments": {"city": "Казань", "units": "k"}},
        ]}
    if any(m["is_error"] for m in tools) and len(tools) == 2:
        return {"tool_calls": [
            {"id": "c3", "name": "get_weather", "arguments": {"city": "Казань", "units": "f"}},
        ]}
    return {"content": "Москва: 5 °C, Казань: 37.4 °F"}

def run(user_text, max_steps=4):
    messages = [{"role": "user", "content": user_text}]
    for _ in range(max_steps):
        reply = fake_llm(messages)
        if "tool_calls" not in reply:
            return reply["content"]
        messages.append({"role": "assistant", "tool_calls": reply["tool_calls"]})
        for call in reply["tool_calls"]:          # независимые вызовы можно запускать параллельно
            messages.append(execute(call))
    return "превышен лимит шагов"

print(run("Какая погода в Москве и Казани?"))   # Москва: 5 °C, Казань: 37.4 °F
```

Обратите внимание: вызов `c2` не падает с исключением, а возвращает `tool_result` с `is_error=True` и текстом «units: допустимо ['c', 'f']». Заглушка «видит» ошибку и повторяет вызов правильно — так и должна вести себя настоящая модель.

## Подводные камни

- **Расплывчатое описание.** «Делает разные вещи с данными» — модель не поймёт, когда это вызывать. Описывайте цель и условия применения.
- **Нет валидации.** Аргументы от модели — это недоверенный ввод; передавать их в код, SQL или командную строку «как есть» опасно.
- **Скрытые ошибки.** Если не сообщить модели о сбое, она может «додумать» результат.
- **Путаница идентификаторов.** Результат без правильного `tool_call_id` нельзя сопоставить с вызовом, особенно при параллельных вызовах.
- **Огромные результаты.** Вывод в мегабайты забивает контекст; обрезайте или суммируйте его.
- **Инъекции через результаты.** Текст внутри результата (веб-страница, письмо) может содержать «инструкции»; считайте его данными, а не командами.
- **Нет `max_steps`.** Модель может бесконечно повторять неудачный вызов.

## Итоги

- Модель не выполняет функции, а возвращает структурированный запрос: имя и аргументы.
- JSON-схема описывает инструмент; качество описания влияет на выбор функции.
- Цикл: tool_call → проверка и выполнение → tool_result → снова модель.
- Независимые вызовы можно запускать параллельно, но результаты возвращают по идентификаторам.
- Валидируйте аргументы, возвращайте ошибки как результаты и ограничивайте число шагов.
